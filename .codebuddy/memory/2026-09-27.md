## 手环9陶瓷版用户卡在第一步的归因分析
- 新增文档 `第一步连接失败分析-手环9陶瓷版.md`（commit cb98981 → adfa226，bump 0.5.5）。

## 第八轮：EvBox 工具箱能否共用同一 APK 的分析（文档）
- 新增文档 `docs/evbox-shared-apk-analysis.md`。
- **决定性结论**：interconnect 配对是"APK applicationId == 快应用 manifest.package"，且 SDK `sendMessage(nodeId, byte[])` **不接受目标包名** → **一个包名的 APK 只能对一个快应用**；"共用一个 APK 同时服务 EV 课程表 + EvBox"**不可行**。
- 两快应用包名不同（`...classschedule` vs `...evbox`），但**签名是同一把**（指纹均为 `466a1e83…9a11`）。
- **推荐方案**：一套源码 + **两个包名变体**（`apk/build.sh` 已在用 sed 注入 label，同一处再注入 `package` 即可）；差异清单 = 包名/label/图标/`launchWearApp` 的 PEER_PKG/数据域/动作集合/版本线/日志 TAG。建议把域与动作抽成配置对象。

## 讨论（无代码）：变体模式确认 + "动态包名"可行性
- 用户确认认可"一套源码 + 多变体"的基本模式；用户原话理解为"源码里有个分支直接导出另一个包"→ **纠正：这是构建变体（`APP_VARIANT`），不是 git 分支**；好处是共用代码天然共用，差异点集中且显式。
- 用户补充：两边界面/功能差异可能都很多 → 对应 P1 的**物理分层**（`src/common` + `src/ev` + `src/evbox`），差异越大越值得做分层；共用的正是"传输/保活/激活/埋点"这些难写的部分。
- 用户提问：见过某软件"通过同步器读取不同手环、功能几乎一致"，猜测是**动态识别包名**让用户选。讨论结论：
  1. **运行时动态包名 = 做不到**：`applicationId` 在安装期固定，系统按包名识别应用，不能运行期切换。
  2. 若指**多个手环设备**：完全可行（`getConnectedNodes()` 返回列表让用户选 nodeId）——**我们现在是缺口**（代码里只取 `nodes.get(0)`，多设备会连错）。
  3. 若指**两个手环快应用**：interconnect 的配对键是"包名+签名"，一个 APK 只能对上一个；替代路径只有 ① 两个 APK（我们的变体方案）② **绕开 interconnect**：AstroBox 插件（宿主通道）或自己走 BLE 直读数据层（Gadgetbridge 那一类）——"功能几乎一致"通常说明它面对的是**手环数据**而不是某个快应用。
  4. 可选澄清实验（15 分钟）：**签名不变、只改 APK 包名**，看能否 ping 通 EV 课程表。通 → 绑定键其实只有签名（则"一个 APK 服务多个快应用"可行）；不通 → 包名确为硬键，维持两变体。
- 建议：维持"一套源码 + 两变体"；若要"一个入口管多个手环快应用"，走 AstroBox 插件那条线。
