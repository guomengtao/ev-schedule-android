# 手表通知（验下行）为什么没装 EV 课程表也能用？

> 关联代码：`apk/src/.../SyncEngine.java`（`notifyTest` / `notifyWatch`）、`DebugActivity.java`（「手表通知(验下行)」按钮）、`MessageActivity.java`（发留言时同步推送）
> 配套版本：v0.5.22 起有 `notifyTest`；发留言同步推手表通知为本次新增

## 一、一句话结论

「手表通知(验下行)」走的是 **`NotifyApi.sendNotify`**，这条通道由**小米运动健康**把手机上的通知转发到手环，是**系统级的通知转发**，跟「EV 课程表」这个快应用**完全无关**。

所以：**手环上装不装 EV，都不影响这条通知。** 只要手机装了「小米运动健康」、且手环已连接授权，点一下就能让手环弹通知。

## 二、APK 里的两条「手机 → 手环」通道（别搞混）

| 通道 | API | 是否依赖 EV 快应用 | 用途 |
|---|---|---|---|
| **手表通知（下行验证）** | `Wearable.getNotifyApi().sendNotify(nodeId, title, msg)` | ❌ 不依赖 | 让手环弹一条系统通知（本功能） |
| **留言 / 聊天（interconnect）** | `Wearable.getMessageApi().sendMessage(nodeId, bytes)` + `{"action":"chat",...}` | ✅ 依赖 | 把报文发给 EV 快应用，EV 存收件箱 + 长震动 |

这就是为什么「验下行」按钮和「留言」是**两回事**：

- 验下行 = **不碰任何数据**、不跟 EV 对话，纯粹证明「手机 → 手环」这条物理链路通不通；
- 留言 = 走 EV 的私有协议，EV 必须装了、且在前台/常驻，才能收到并落收件箱。

## 三、为什么「手表通知」不需要 EV

小米运动健康（以及手环固件）本身就支持「**通知转发**」：手机上授权过的 App 产生通知，会被推到手环上以卡片形式展示。`NotifyApi.sendNotify` 就是 APK 直接调用这个能力，把「标题 + 内容」塞进转发队列。

整个过程：

```
APK  ──sendNotify──▶  小米运动健康（手机端）  ──蓝牙──▶  手环通知中心  ──▶  弹卡片
```

- 全程**没有** APK ↔ EV 的 interconnect 点对点连接；
- 手环上**没有** EV 也能弹通知，因为通知是「手环系统」在接，不是 EV 在接；
- EV 装了也**不会**因此收到这条通知（它不在 interconnect 层），它只是「刚好也弹了一条系统通知」而已。

> 这也是为什么文档里反复把它称作「零风险下行验证」：**它不读、不改、不碰任何课表/用户数据**，只验证通道。

## 四、新增功能：发留言的同时，把内容也推成「手表通知」

既然手表通知不依赖 EV，而原来的留言（chat）需要 EV 才能收到，那最自然的产品改进就是：

> **用户在手机发一条留言时，除了走 EV 的 chat 通道，再额外用 `sendNotify` 把正文推一条到手环。**
> 这样**即使手环没装 EV 课程表，用户也能在手环上看到这条留言内容**。

### 实现要点

`SyncEngine.notifyWatch(title, msg, cb)`：封装 `sendNotify`，内容与 `notifyTest` 同源，只是文案由调用方给。

`MessageActivity.flush()`（逐条补发 pending 留言处）在真正发报文前增加：

```java
if (!pending.optBoolean("notified", false)) {
    e.notifyWatch("手机留言", text, new SyncEngine.Cb() {
        @Override public void on(boolean ok, String m) { /* 尽力推送，不阻塞留言发送 */ }
    });
    try { pending.put("notified", true); save(); } catch (Throwable ignored) {}
}
```

- `notified` 标记写进每条留言，保证**每条只推一次**（flush 超时重发时不会重复弹手环通知）；
- 手表通知是**尽力而为**（best-effort），无论成功与否都不影响 chat 报文本身的发送/补发逻辑；
- 手环装了 EV 时：会**同时**收到 chat 气泡（EV 收件箱）和这条系统通知——两者并存，不冲突。

### 适用边界（重要）

| 维度 | 说明 |
|---|---|
| 方向 | 仅 **手机 → 手环**，手环**不能**通过这条通知回复（它不是聊天通道） |
| 依赖 | 需「小米运动健康」已装、手环已连接、且 `notify` 权限已授权（调试页「授权」按钮） |
| 内容长度 | 手环通知有展示长度限制，`sendNotify` 由 SDK/固件截断，超长正文会被截短 |
| 与 EV 的关系 | 不装 EV 也能用；装了 EV 也**不**走 EV 协议，纯系统通知 |
| 送达确认 | 没有 ack；发出去即视为尽力送达，不保证手环一定显示（与 chat 的 `chat_ack` 不同） |

## 五、怎么验证

1. 手环**不装** EV 课程表，只装「小米运动健康」并连上；
2. 进调试页点「手表通知(验下行)」→ 手环应立即弹一条「EV 同步器 / 下行测试」；
3. 进留言页发一条 → 手环应弹「手机留言 / <你写的内容>」；
4. 再装回 EV、发同一条 → 手环**既**有系统通知（本功能）**又**有 EV 的留言气泡（chat 通道）。

## 六、小结

「手表通知(验下行)」是一个被低估的好能力：**它用系统级通知转发绕开了 EV 装机的硬前提**。把它和留言发送结合起来，等于给「没装 EV 的用户」也开了一扇「手机 → 手环」的轻量单向通知窗，无需改 EV、无需新协议，零数据风险。
