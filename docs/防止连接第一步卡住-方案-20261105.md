# 防止「安卓同步器连接第一步卡住」方案

- 日期：2026-11-05 15:49 +0800
- 涉及项目：`ev/ev-schedule-android`（手机端同步器 APK）
- 性质：**方案文档，不含代码改动**
- 触发：USB 真机（荣耀畅玩7X / Android 8.0 / EMUI 8.0）上，四步排查第一步停在「执行中…」不返回

---

## 零、结论与问题定性

先要把「这个错误」定义准，否则防错会防偏：

| 说法 | 是否可防 | 说明 |
|---|---|---|
| 连不上小米运动健康的穿戴服务 | ❌ 不能保证 | 取决于手机系统、Mi Fitness 版本、后台策略、账号状态，属外部环境 |
| **第一步无限「执行中…」、无失败提示、无法重试、后续三步全被跳过** | ✅ **必须防住，且能 100% 防住** | 这是纯客户端缺陷：缺超时 + 缺前置判定 |

因此本方案的目标是：

> **把「不可控的环境失败」稳定地转成「有明确结论、可重试、可降级」的可控失败。**
> 允许连接失败，但绝不允许界面无期限地等一个可能永不触发的回调。

## 一、现场证据（2026-11-05 实测，只读）

| 项 | 实测值 |
|---|---|
| USB 设备 | `BTF4C17222009588` |
| 机型 / 系统 | `BLN-AL20` 荣耀畅玩7X · Android 8.0.0 · SDK 26 · EMUI 8.0.0 |
| 同步器 | `com.application.watch.classschedule` v0.5.181（11-05 12:36 +0800 更新） |
| 小米运动健康 | **`com.mi.health` 3.59.1**（新版包名，非 `com.xiaomi.wearable`） |

关键代码事实：

1. `apk/src/.../SyncEngine.java:1535` `step1Service()` 只调
   `Wearable.getServiceApi(ctx).getServiceApiLevel()`，挂 `addOnSuccessListener` /
   `addOnFailureListener`，**没有任何超时**。
2. 同文件 `:1555` `step2Nodes()` **有** 10 秒超时，注释原文：
   > 「必须带超时——小米运动健康偶尔不回调（蓝牙断/手环 USB 调试模式），不加超时会永远卡在第二步」
3. `apk/src/.../DebugActivity.java:625` `runStep()` 把状态置 `RUNNING("执行中…")` 后直接等回调；
   `:642` `runAll()` 依赖前一步 `OK` 才执行下一步 —— 第一步不返回，后面三步全部被跳过。
4. `xms-wearable.jar` 的绑定逻辑（`com/xiaomi/xms/wearable/d.class#a()`，反编译确认）：
   ```
   Intent("com.xiaomi.wearable.XMS_WEARABLE_SERVICE")
     → setPackage("com.mi.health")
     → resolveService 探测不到，才回退 setPackage("com.xiaomi.wearable")
     → bindService(intent, conn, BIND_AUTO_CREATE)，返回值存字段 d
   ```
   `d` 只记录 bindService 的布尔返回，**上层 `step1Service()` 完全没有消费它**。
5. `SyncEngine.java:198` 构造时 `api = Wearable.getMessageApi(c)`；若 `api == null`，
   `step1Service()` 会立即返回「还没装小米运动健康」。现场表现是「一直转圈」而非立即报错，
   说明 `api != null`，卡点在 **ServiceApi 的跨进程绑定/回调**，不是「App 没装」。

已有可复用结论：

- `docs/apk-tracking-telemetry-spec.md` §四：鸿蒙 NEXT「卓易通」沙箱内 APK 连不上沙箱外的
  穿戴服务，**必然卡第一步**。本机型是 EMUI 8（真 Android），不适用该分支，但说明
  「第一步失败」是已知高危人群，需要区分环境而不是统统当 bug。
- `ev/class-schedule/docs/激活入口顺序调整方案-20261104.md`：安卓路径依赖
  `同步器 → 小米运动健康 → 手环 SPP 会话` 三段串联，兑换码路径只依赖一个网页，
  是确定性兜底。

## 二、根因链（三层，缺一层都不会表现为「卡死」）

```
① SDK 绑定不确定的服务
   com.mi.health 3.59.1 是否声明 XMS_WEARABLE_SERVICE 未做前置校验；
   EMUI 8 的后台/自启动限制可让 bindService 成功却拿不到 binder。
        ↓
② 绑定结果无人消费、第一步无超时
   bindService 返回值只存进 SDK 内部字段 d；step1Service 既不检查也不超时，
   回调不来就永久停在 RUNNING。
        ↓
③ UI 没有失败出口
   DebugActivity 后续三步靠「前一步 OK」串行触发，第一步挂起 → 全链路停摆；
   用户看不到错误、看不到重试、也看不到降级入口。
```

**为什么「小米健康显示已连上手环」帮不上忙**：第一步检测的是
「能不能调用小米运动健康暴露的穿戴服务 API」，与蓝牙链路、手环在线状态是两条独立通道。
手环连得好好的，跨进程服务照样可能 bind 不上。UI 上把失败统称「识别不到」，
会持续误导排查方向。

---

## 三、防复发方案

分层原则：**P0 先把「无限等待」这个错误形态消灭；P1 让失败可自救；P2 让以后不用接 USB 就能定位。**

### P0-1 超时能力抽象成公共层（最重要）

不要只给第一步补一个 `postDelayed` —— 那正是这次踩坑的模式：第二步加了、第一步忘了。
把超时抽成四步共用的唯一入口：

```java
// 建议新增：SyncEngine.withTimeout(Cb cb, long ms, String fallback)
// 任何一步都必须经它包装，禁止直接把原始 SDK 回调交给 UI
```

| 步骤 | 建议超时 | 兜底文案要点 |
|---|---|---|
| ① 初始化服务 | 8s | 说清是「叫不动小米运动健康的服务」，不是「手环没连」 |
| ② 查找设备 | 10s（已有，保持） | 保留现有「打开小米运动健康重新连」引导 |
| ③ 申请权限 | 8s | 指向系统权限页 |
| ④ ping EV | 15s | 指向手环端 EV 是否安装/在前台 |

**加一条硬约束**：`DebugActivity.runStep()` 里若检测到某步没有经过 `withTimeout` 包装，
直接判 FAIL（可用断言或静态检查），防止以后新增第五步时再次遗漏。

**验收**：在测试包里把 SDK 回调人为吞掉（不调 success/failure），四步都必须在各自超时内
落到 FAIL 并给出文案，界面不再出现任何长期 `RUNNING`。

### P0-2 绑定前体检（Preflight），让会卡死的分支根本进不去

在四步之前，用 `PackageManager` 做一次零网络、零 SDK 依赖的判定：

1. `com.mi.health` 与 `com.xiaomi.wearable` 哪个存在、版本号；
2. 用 `resolveService(new Intent("com.xiaomi.wearable.XMS_WEARABLE_SERVICE"), 0)`
   分别探测两个包，**确认 action 是否真的被声明**；
3. 系统品牌/os_brand（复用 `apk-tracking-telemetry-spec.md` §四的判定顺序）。

判定结果三选一：

| 结果 | 行为 |
|---|---|
| 服务可解析 | 正常进四步 |
| 包在、服务不可解析 | **不进连接流程**，直接给「当前小米运动健康版本不提供穿戴服务」+ 兑换码入口 |
| 鸿蒙 NEXT / 卓易通 | 直接标「本环境不支持自动同步」，不尝试 bind |

这一条是「防止错误出现」的主防线：**第一步还没开始，就已经知道它会不会卡。**

**验收**：`com.mi.health` 3.59.1 上若 `resolveService` 无结果，App 不再出现「执行中…」，
而是直接显示可操作结论。

### P1-1 单一连接状态机

`SyncEngine` 单例维护显式状态：

```
IDLE → PREFLIGHT → BINDING → BOUND → NODE_FOUND → READY
                     └──────────→ FAILED(reason, step, retryable)
```

- 任何超时/异常/回调不达都收敛到 `FAILED`，页面只渲染状态机，不自己等待回调；
- 失败带 `retryable` 标记与退避（1s → 3s → 8s），避免连点造成并发 bind；
- 复用现有 `BandActivity.scheduleAutoDebugIfStuck()` 的 1.5s 兜底思路，但改为
  「FAILED 才进排障页」，而不是「未连接就靠猜」。

### P1-2 失败必给降级出口

连续 2 次 FAILED 后，页面固定展示两条可操作项：

1. 「打开小米运动健康并允许后台运行」（EMUI/鸿蒙要额外给自启动设置引导）；
2. **「改用兑换码激活」** —— 直接进 `ev/class-schedule` 的确定性路径，不碰蓝牙、不碰服务。

依据：`激活入口顺序调整方案-20261104.md` 已论证兑换码是唯一确定性路径。
这样即使自动同步长期不可用，用户也不会被卡死在功能门外。

### P2 可观测：以后不接 USB 也能定位

在 `apk-tracking-telemetry-spec.md` 已有字段
`connect_last_fail_step` / `connect_last_fail_reason` 基础上补齐环境字段：

| 新增字段 | 用途 |
|---|---|
| `mi_health_pkg` / `mi_health_ver` | 区分 `com.mi.health` 与老包名、定位版本回归 |
| `service_action_resolved` | bind 前体检结论，直接区分「服务不存在」与「bind 被拒」 |
| `bind_service_result` | 记录 SDK 里那个目前被丢弃的 `d` 值 |
| `os_brand` / `emui_version` / `android_sdk` | 区分 EMUI 后台限制、鸿蒙沙箱、普通小米 |
| `step_elapsed_ms[]` | 四步各自耗时，超时率可统计 |

目标：以后再有人报「卡第一步」，看埋点即可判定
「服务不可解析 / bind 被拒 / 回调超时 / 沙箱环境」，不必借 USB 抓现场。

## 四、落地顺序与最小改动集

| 序 | 动作 | 文件 | 规模 |
|---|---|---|---|
| 1 | 抽 `withTimeout`，四步统一接入 | `SyncEngine.java` | 小 |
| 2 | `runStep` 增加「未包装即 FAIL」约束 | `DebugActivity.java` | 小 |
| 3 | Preflight 体检 + 三分支 | `SyncEngine.java`（新增 `preflight()`） / `DebugActivity.java` | 中 |
| 4 | FAILED 状态与降级引导 | `BandActivity.java` / `DebugActivity.java` | 中 |
| 5 | 埋点字段补齐 | `Analytics.java` / 服务端 | 中 |

**只做 1+2 就能消灭「无限卡住」这个错误表现**；3 起才会真正减少连接失败率；
4 保证失败也不流失用户。建议 1+2+3 同批上线，4、5 随后。

## 五、验收矩阵（真机，非模拟器）

模拟器（NuttX / Vela）**验不了这条链路**：它没有小米运动健康，也没有跨进程穿戴服务。
必须用 USB 真机：

| 机型 | 关注点 | 期望 |
|---|---|---|
| `BLN-AL20` / EMUI 8 + `com.mi.health` 3.59.1（现场机） | 服务是否可解析、bind 是否被后台策略拒 | 不再无限转圈；给出明确结论 + 兑换码入口 |
| 小米手机 / 较新 Android + 同版本 Mi Fitness | 正常路径回归 | 四步全 OK，同步可用 |
| 鸿蒙 NEXT / 卓易通 | 沙箱环境 | Preflight 直接判不支持，不进连接流程 |
| 任意机型 + 强制卸载/停用小米运动健康 | 极端降级 | 立即给「未安装」结论，不等待 |

补充用例：**人为吞回调**（测试包里让 SDK 只 bind、不回调）验证四步都在超时内落 FAIL，
这是防复发的核心回归项，每次改连接代码都要跑。

---

## 六、边界：本方案不做的事

- 不修改 `xms-wearable.jar`，不逆向或替换小米 SDK；绑定策略由 Preflight 绕开，不与之对抗。
- 不承诺「一定能连上手环」——后台策略、账号登录、Mi Fitness 版本都由外部决定。
- 不改动 `ev/class-schedule` 手环端；兑换码兜底路径按现状复用。
- 不改 UI 视觉规范，仅新增失败态文案与两个操作入口。

---

## 七、一句话复盘

这次不是「小米健康又识别不到手环」，而是
**客户端把一个可能永不回调的跨进程调用，直接挂在了没有超时、没有降级出口的 UI 上**。
防复发的抓手不是修某一台手机，而是：
**任何异步调用都必须经过超时层，任何失败都必须有明确结论和可走的下一条路。**
