# APK 定位分析：只做同步器，还是做成「能独立用的课程表」？

> 日期：2026-09-27
> 触发：桌面名改为「Ev课程表」后，首屏到底该显示"同步功能"还是"课程表"？要不要让 APK 也能独立当课程表用？
> 依据：基于当前代码现状逐条盘点（v0.5.23），不做空想推演

---

## 一、结论先行

**推荐定位：手环课表的「手机端管理器」——名字可以叫「Ev课程表」，但不要做成独立课程表 App。**

一句话表达：

> APK 不是第二个课程表，它是**手环那张课表的遥控器**：手机上能看、能改、能导、能推，但**课表的唯一真源仍然在手环**。

对应到首屏（回答"显示同步还是课表"）：

```
首屏 =  连接状态（一眼知道通不通）
      + 课表快照（只读，从手环拉下来的本周课表）   ← 兑现"Ev课程表"这个名字
      + 同步动作入口（导入/导出/设置…）           ← 保留它存在的理由
```

**不做**：本地课程表数据库、周视图网格编辑器、上课提醒、桌面小组件。

## 二、现状盘点（代码事实，不是想象）

| 维度 | 现状 | 证据 |
|---|---|---|
| 桌面名 | `EV Sync v0.5.23`（版本号拼在名字里） | `build.sh` `LABEL_BASE="EV Sync"` |
| App 内标题 | 「EV 课程表」+ 副标题「安卓同步器 vX」 | `HomeActivity` |
| 课表数据存在哪 | **只在手环**。APK 每次要看都得现拉 | `HomeActivity.loadProfile()` 拉 `export`；`lastExportJson` 只存内存 |
| 多套课表 | 手环侧 `list_schedules`，APK 只做选择/读取 | `TransferActivity.loadSchedules()` |
| 首页能看到课表吗 | 只能看到**一个数字**：「课表 N 节」 | `e.courseCount`，无任何课程明细 |
| 能改课表吗 | 能，但**是手写 JSON**（编辑框），不是表单 | `TransferActivity` 导出页 JSON 框 +「更新到手环」 |
| 有周视图/网格 UI 吗 | **没有** | 全仓无 grid 课表视图 |
| 有本地持久化吗 | **没有**（导出需用户主动"保存到下载目录"） | `saveToFile()` 是用户主动动作 |
| 离开手环还能用吗 | **基本不能**（唯一例外：刚加的"手表通知"走系统级 NotifyApi） | `SyncEngine.notifyWatch` |

**关键判断**：APK 目前对课表是**"过路"**的——数据从手环来到手环去，手机只是通道和编辑台。

## 三、三条路线的正面比较

### 路线 A：纯同步器（现状）

- 首屏：连接进度 + 按钮列表。名字符实（"同步器"）。
- ✅ 聚焦、轻、维护成本低、不与手环产品抢戏。
- ❌ 用户装完觉得"这 app 没内容"；打开是一排按钮，没有"我的课表"的归属感；品牌弱。
- ❌ 名字若叫「Ev课程表」会**名不副实**（见第五节）。

### 路线 B：独立课程表 App + 同步到手环

即"手机上也是完整课程表，能独立用，也能推给手环"。

- ✅ 独立价值、留存高、"课程表"是真实刚需、名字名副其实。
- ❌ **工作量是第二个完整产品**：本地库 + 周视图网格 + 增删改表单 + 节次/单双周/调休 + 提醒 + 小组件。
- ❌ **正面撞成熟竞品**（超级课程表、WakeUp 等），我们没有差异化优势，且**手环才是我们的护城河**，手机端不是。
- ❌ **双源冲突**（最致命）：手机一套、手环一套 → 必须定义"谁的改动赢"、增量还是覆盖、时间戳还是版本号。我们一路走来的架构前提是**手环唯一真源**，推翻它等于重写两端的同步语义。
- ❌ **能力不对齐**：手机端做出了手环不支持的字段（单双周、第几周）→ 同步时必然降级或丢数据。
- ❌ **两套 schema 维护**：Vela 端 + Android 端。现在光是"格式 A（按天分组）"和"一条课一个对象"的互转就已经有专门的坑（`flattenFormatA` / `toCourseArray` 就是证据），再来一套只会更痛。

### 路线 C：手环课表的手机端管理器（**推荐**）

- 首屏：连接状态 + **只读课表快照** + 同步入口。
- 编辑走**「拉 → 改 → 推」临时态**：数据仍以手环为真源，手机上改完立即推回，**不落本地库**。
- ✅ 兑现"Ev课程表"这个名字（首屏看得见课表内容）。
- ✅ **不引入双源**，零冲突解决成本。
- ✅ 复用现有协议（`export` / `list_schedules` / `import`），EV 侧几乎不用改。
- ✅ 解决真实痛点：**在 1 寸手环屏上敲课表很痛苦**，手机端编辑器是刚需。
- ⚠️ 离线不可用（没连手环时看不到课表）——这是**主动接受的取舍**，不是缺陷。

## 四、回答"首页显示同步还是课表"

**两个都要，但有主次：课表是"内容"，同步是"动作"。**

- 用户打开一个叫「Ev课程表」的 App，**第一眼想看到的是课表**（内容），不是"连接成功"（状态）。
- 但 APK 离开手环就没有内容 → 所以**必须先有连接状态**（否则课表区是空的，用户会以为坏了）。

推荐首屏结构（自上而下）：

1. **连接状态条**（一行，成功/失败 + 设备名 + 版本）
2. **本周课表快照**（只读卡片，按天列出今天的课 / 本周概览；未连接时显示"连接手环后查看"）
3. **动作区**：导入课程表 / 导出课程表 / 设置 / 调试（现状按钮，折叠在下方）

这样：连上后用户看到的是"我的课表"，顺便能操作同步；没连上时状态条明确告诉他为什么没内容。

## 五、改名「Ev课程表」的连带影响（**必须配套处理**）

改名的好处是品牌统一（用户装了能认出是 EV 课程表的配套）；但**风险是期望落差**：

> 用户在桌面看到「Ev课程表」→ 点开 → 如果首屏只有"连接成功 + 一排按钮"，心理落差很大，会认定"这 app 是干嘛的？"

所以**改名和首屏课表快照必须一起做**：

| 必做 | 说明 |
|---|---|
| 首屏加只读课表快照 | 兑现名字，让"课程表"三个字立住 |
| 副标题明确身份 | 现状「安卓同步器 vX」可改为「手环课表 · 手机端」，一句话说清它是配套 |
| 桌面名去掉版本号 | 已完成（`build.sh` 不再拼 `v$VERSION_NAME`），版本号在 App 内首页看 |

> 反过来说：**如果不打算做首屏课表快照，那名字就不该叫「Ev课程表」**，老老实实叫「EV 课程表同步器」更诚实、差评更少。

## 六、如果将来真要"脱离手环也能用课表"（分级路径）

按投入从低到高，**建议最多做到 L2**：

| 级别 | 能力 | 是否推荐 |
|---|---|---|
| **L0（现状）** | 只有数字「课表 N 节」 | 已过时 |
| **L1** | 首屏只读课表快照（连上才有） | ✅ **推荐，先做这个** |
| **L2** | 结构化编辑（点一格改课，替代手写 JSON），拉→改→推，不落库 | ✅ 推荐，体验提升最大 |
| **L3** | 本地缓存最近一次课表，**断连时可读**（不可编辑） | ⚠️ 可选，需处理"陈旧数据"提示 |
| **L4** | 完整本地课表 App（可离线增删改 + 双向同步 + 冲突解决） | ❌ **不建议**：等于第二个产品，且撞竞品 |

L3 的"缓存"和 L4 的"独立"有本质区别：**缓存是副本（只读、可丢弃、标为陈旧），独立是真源（可写、需合并）**。守住这条线就不会掉进双源陷阱。
