# Ev课程表 Android 端自动升级实现方案

> 分析日期：2026-09-28  
> 范围：`apk/`（Ev课程表 / EvBox Sync 双变体，纯 Java，无 Gradle）  
> 结论先行：**做「简易整包自更新」，一个 `UpdateChecker.java`（约 250 行）+ 一个静态 JSON 文件即可，半天工作量。** 不做增量、不做热更、不做静默安装。

---

## 1. 原理一句话

App 启动时后台 GET 服务端一个 JSON（最新版本号 + APK 地址）→ 与本地 `versionCode` 比较 → 更大则弹窗 → 下载 APK → 调系统 API 安装。服务端甚至不需要程序，**一个静态 JSON 文件就够**。

## 2. 项目现状盘点（方案设计的依据）

| 现状 | 对升级方案的影响 |
|---|---|
| 版本号唯一真源 `version.env`，`build.sh` 构建后自动 bump | `update.json` 里的 `versionCode` 必须= **刚发布包**的 code；建议由 build.sh 自动生成，杜绝手填错 |
| 双变体：`ev`(0.5.x/code 同步) 与 `evbox` 两条独立版本线 | 服务端 JSON 按 **变体分文件**：`update-ev.json` / `update-evbox.json` |
| 已有 `Net.java`（HttpURLConnection 封装，BASE=`https://app-auth.gudq.com`，仅 POST） | 加两个方法即可复用：`get()` 拉 JSON、`download()` 流式下载；HTTPS 已就绪，**无明文流量坑** |
| 纯 framework，**无 androidx** | ❌ 不能用 `androidx.core.content.FileProvider` → 安装方案选型受影响（见 §4） |
| 全部 `Activity`（非 AppCompat）+ `android.app.AlertDialog` | 弹窗 UI 直接用 AlertDialog，零新依赖 |
| Manifest 已有 `INTERNET` 权限 | 无需新增网络权限 |
| 签名：优先 RPK 密钥（PEM/pkcs8），否则 `keystore.jks` 自签 | **覆盖安装的前提是签名不变**。确定用哪套签名后不要换；签名文件丢失 = 全部用户只能卸载重装 |
| 真机实测环境：荣耀 BLN-AL20 (EMUI, 1080x1920) | 安装确认弹窗无法绕过（见 §7），UI 流程按「手动确认」设计 |
| `minSdk 24 / targetSdk 34` | `file://` 已被禁 → 排除老式 FileProvider-URL 直传；PackageInstaller API 完全可用（API 21+） |

## 3. 服务端设计：一个静态 JSON 文件

路径建议：`https://app-auth.gudq.com/ev/update-ev.json`（evbox 同理），内容：

```json
{
  "versionCode": 31,
  "versionName": "0.5.30",
  "url": "https://app-auth.gudq.com/ev/EVSyncProbe-v0.5.30.apk",
  "sha256": "abcd1234…",
  "force": false,
  "log": "修复连接提示文案；底栏遮挡适配"
}
```

- **比较键只有 `versionCode`**（单调递增），`versionName` 仅展示；`sha256` 下载后校验（防截断/篡改，M2 加）；`force: true` 时弹窗不可取消。
- 上传物 = `dist/` 里的 APK + JSON 两个文件，服务器无任何逻辑。

### 让 build.sh 自动产出 update.json（关键防错）

版本号 bump 发生在构建**之后**，所以构建时刻 `$VERSION_CODE` 就是「这个包自己」的 code，直接在 build.sh 签名步骤后追加：

```bash
# --- 生成升级描述文件（与 APK 一起上传服务器）---
SHA=$(shasum -a 256 "$OUT" | cut -d' ' -f1)
cat > "dist/update-${VARIANT}.json" <<EOF
{"versionCode":$VERSION_CODE,"versionName":"$VERSION_NAME",
 "url":"https://app-auth.gudq.com/ev/${OUT_NAME}-v${VERSION_NAME}.apk",
 "sha256":"$SHA","force":false,"log":""}
EOF
```

发布流程因此变成三步：`build.sh` → 上传 `dist/*.apk` + `dist/update-*.json` 到服务器 → 完事。**不存在「忘了同步版本号」这类事故**。

## 4. App 侧安装方案选型（无 androidx 是核心约束）

| | 方案 A：PackageInstaller 流式安装 | 方案 B：下载文件 + FileProvider + ACTION_VIEW |
|---|---|---|
| 依赖 | 纯 framework（API 21+） | 需自写 ~40 行 ContentProvider（androidx 不可用） |
| Manifest 改动 | 仅加权限 | 加权限 + `<provider>` + `file_paths.xml` |
| 磁盘占用 | **零临时文件**（HTTP 流直写安装 session） | 完整 APK 落盘（~24MB） |
| 代码量 | ~80 行 | ~60 行 + Provider 40 行 |
| 兼容性 | API 24 起无问题；华为实测走标准确认弹窗 | 兼容性极好，但多一套文件管理 |
| 结论 | ✅ **推荐** | 备选（A 在个别 ROM 上异常时降级用） |

## 5. App 侧改动清单

| 文件 | 改动 |
|---|---|
| `Net.java` | 新增 `get(url, cb)`（拉 JSON）和 `download(url, out, progressCb, done)`（流式下载+进度回调） |
| `UpdateChecker.java`（新增，核心） | 见 §6 骨架：检查→解析→比较→弹窗→安装，全链路 |
| `AndroidManifest.xml` | `<uses-permission android:name="android.permission.REQUEST_INSTALL_PACKAGES"/>` |
| `HomeActivity.java` | `onCreate` 尾部调 `UpdateChecker.check(this, false)`（静默检查，失败不提示） |
| `SettingsActivity.java` | 加「检查更新」入口，调 `check(this, true)`（手动检查，失败弹 toast） |

存储路径（若走方案 B）：`getExternalFilesDir(null)`，**不需要任何存储权限**，卸载即清。

## 6. UpdateChecker 关键骨架

```java
public final class UpdateChecker {
    /** silent=false 时失败/无更新均给反馈；silent=true 仅在真有新版时打扰 */
    public static void check(final Activity a, final boolean silent) {
        Net.get(BASE + "/ev/update-ev.json", (code, body) -> {
            if (code != 200 || body == null) { if (!silent) toast(a, "检查失败"); return; }
            JSONObject j = new JSONObject(body);
            int remote = j.getInt("versionCode");
            int local  = a.getPackageManager()
                          .getPackageInfo(a.getPackageName(), 0).versionCode;
            if (remote <= local) { if (!silent) toast(a, "已是最新版本"); return; }
            showUpdateDialog(a, j);   // AlertDialog：log + 「立即更新」/「取消」
        });
    }

    private static void install(Activity a, InputStream apkStream) throws Exception {
        // 方案 A：HTTP 流直接写进 PackageInstaller session，无临时文件
        PackageInstaller pi = a.getPackageManager().getPackageInstaller();
        PackageInstaller.SessionParams p = new PackageInstaller.SessionParams(
                PackageInstaller.SessionParams.MODE_FULL_INSTALL);
        int sessionId = pi.createSession(p);
        PackageInstaller.Session s = pi.openSession(sessionId);
        OutputStream out = s.openWrite("ev.apk", 0, -1);
        byte[] buf = new byte[8192]; int n;
        while ((n = apkStream.read(buf)) > 0) { out.write(buf, 0, n); }
        s.fsync(out); out.close();
        // commit 后系统弹「是否安装」——这是 ROM 安全设计，无法静默（见 §7）
        Intent cb = new Intent("ev.INSTALL_DONE").setPackage(a.getPackageName());
        s.commit(PendingIntent.getBroadcast(a, sessionId, cb,
                PendingIntent.FLAG_IMMUTABLE).getIntentSender());
        s.close();
    }
}
```

Android 8+ 权限引导（安装前检查一次）：

```java
if (!a.getPackageManager().canRequestPackageInstalls()) {
    // 跳「允许安装未知应用」设置页（华为上叫「外部来源应用下载」），回来后重试
    a.startActivity(new Intent(Settings.ACTION_MANAGE_UNKNOWN_APP_SOURCES,
            Uri.parse("package:" + a.getPackageName())));
    return;
}
```

## 7. 坑点清单（按优先级）

1. **无法完全静默安装，必须用户点确认** —— ROM 安全设计（含原生 Android 8+），别在产品文案里承诺「自动完成升级」；流程按「弹窗→下载→系统确认→完成」设计。
2. **签名一致性是覆盖安装的生死线** —— ev 变体当前签名源是 RPK 密钥目录（`tom/class/class/sign`），一旦发过线上包就锁死这套签名；`keystore.jks` 分支只存在于无 RPK 密钥的机器，两套签名装出来的包**互不覆盖**（会变成「应用未安装」或并存）。发布机上装哪套就要永远用哪套。
3. **`versionCode` 必须单调递增** —— 已装机器上装低 code 包直接 `INSTALL_FAILED_VERSION_DOWNGRADE`；§3 的 build.sh 自动生成机制可杜绝手填错。
4. **JSON 请求必须 HTTPS** —— targetSdk 28+ 默认禁明文；`app-auth.gudq.com` 本就是 HTTPS，无碍，但别图省事换 http 镜像。
5. **华为/EMUI 额外拦截** —— 除「允许安装未知应用」外还有「外部来源应用下载」总开关（真机 BLN-AL20 实测路径：设置→安全→更多安全设置）；引导文案里提一句可少一半售后。
6. **`force: true` 的定义** —— 弹窗不可取消 + 首页拦截（可选）。自用场景建议慎用：没配对手环的用户强制升级意义不大。
7. **下载中断** —— 简易版不做断点续传，失败重下（24MB 包 4G 网络约 10 秒，可接受）；给「重试」按钮即可。

## 8. 分期落地

| 阶段 | 内容 | 工作量 |
|---|---|---|
| **M1 可用** | 服务端 JSON + build.sh 自动产出；`Net.get/download`；`UpdateChecker`（检查/弹窗/PackageInstaller 安装）；Manifest 权限；HomeActivity 静默检查 | ~半天 |
| M2 体验 | 下载进度条、sha256 校验、`force` 处理、「忽略此版本」、设置页手动入口 | ~半天 |
| M3 视需要 | evbox 变体接入（改 URL 后缀即可）、双通道（stable/beta 两个 JSON） | ~1 小时 |

**明确不做**：增量/差分更新（bsdiff 工具链复杂度远超自用收益）、热更新框架（商店封杀 + 复杂度）、静默后台安装（系统不允许）、断点续传。

## 9. 常见误区（写给未来的自己）

- ❌ 「像网页一样刷新代码，不用重装」—— APK 是完整二进制，**所有更新都走安装**；没有热更就没必要研究。
- ❌ 「App 能知道服务器有新包就直接装」—— 必须用户在系统弹窗上点「安装」，任何 ROM 都一样。
- ✅ 升级功能上线后，**发版 = build.sh + 上传两个文件**，流程极简，记得把 `update-ev.json` 的 `log` 字段写成人话（首页弹窗直接展示）。
