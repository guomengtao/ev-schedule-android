# EV 课程表 · 安卓端激活页机制分析 与「APK 激活」新默认流程方案

> 2026-09-29 · 依据：手环端 `tom/class/class/src/pages/activation/activation.ux`、安卓端 `apk/src/.../FastActivateActivity.java`、后端 `app-auth/api/activate.js`、网站 `app-auth/activate.html`。

---

## 一、现状梳理

### 1.1 手环端原流程（高级版页，activation.ux）

| 步骤 | 内容 | 载体 |
|---|---|---|
| ① 购买 | 手环显示「爱发电购买」二维码（`AFDIAN_REDIRECT_URL = /go/ev-timetable?deviceId=…&m=…&r=…&c=…`，带设备与渠道追踪） | 手机扫码 → 跳转爱发电下单 → 获得 **4 位兑换码** |
| ② 兑换 | 手环显示「激活兑换」二维码（`ACTIVATION_URL = /activate.html?deviceId=…`） | 手机打开网页 → 输入 4 位兑换码 → 后端按 deviceId 生成 **18 位激活码** 返显 |
| ③ 写入 | 用户在手环 18 格键盘**手输 18 位数字** | 手环本地校验（`PPCCCCMMDDDD` 结构）+ 落库生效 |

痛点：全程要在手环小屏上扫两个码 + 手输 18 位，步骤多、易输错、上下文割裂（购买在手机、兑换在手机、确认在手环）。

### 1.2 安卓端现有「快速激活」（FastActivateActivity）

流程：`get_device_id`（interconnect 取手环设备ID）→ 用户输入 4 位兑换码（单 EditText，AllCaps + 限长 4）→ `POST /api/activate {deviceId, redeemCode, deviceInfo}` → 拿到 18 位激活码 → interconnect `activate` 写入手环 → 手环回 `ok` + `displayStatus`。

**稳定性上的既有保障（这是本机制的底子，都很扎实）：**
- 后端 `generateActivationCode(productId, device, months, code)` 是**确定性函数**：同一兑换码 + 同一设备重复兑换，得到的 18 位码恒定 → 「同码同设备复用」分支天然幂等，且追加 `<激活码>:<第N次>` 记录不覆盖历史。
- **一码一机**由服务端保证：`used_device_id`（sha256 hash）比对；同设备复用放行；跨设备拒绝（报「已被其他设备使用」）；NA 设备（取不到 ID 的 fallback）单独限额（默认 5 次）。
- IP 限流 + 设备限流 + 全量失败记录（`auth:activation_failure:*`）+ tracking 漏斗（visit/failure/activation）+ Mac 端实时推送，异常可见。
- 写库用 pipeline 且 `reportPipelineFailures` 会把部分失败主动告警，不会静默丢激活记录。
- 安卓端读取设备ID有 fallback 标识提示（`fallback=true` 时警告「重装应用可能失效」）。

**便捷性/体验上的欠缺（本次要补的）：**
1. 兑换码是**单个 EditText**，不是四格分位框；无粘贴自动分位、无自动跳格。
2. **未连接手环时整条流程被卡死**：`loadDeviceId` / `activate` 都直接要求先连接，用户买完码回来若手环不在旁边，只能干等。
3. **没有任何本地暂存**：进程被杀 / 用户中途退出，输入的兑换码就丢了。
4. 购买入口只有一行小字说明「兑换码在爱发电购买后获得」，**没有直达按钮**，用户要自己去找链接。
5. 激活码到手后若写入手环失败（蓝牙瞬断、超时），**18 位码没有留存**，用户重试要重新走一遍服务端（虽然幂等，但体验差）。
6. 多手环场景（`NodeChooser`/`preferredNode`）下没有显式的「目标手环确认」，存在把码写错手环的隐患。

### 1.3 后端协议（不变的部分，新流程全部复用）

- `POST /api/activate`：`{deviceId, redeemCode, deviceInfo}` → `{success, activationCode(18位)}`；429/400/500 均有结构化 `error` 与 `code`（如 `DEVICE_ID_INVALID`）。
- interconnect：`get_device_id` → `{ok, deviceId, deviceId4, fallback}`；`activate`（18位码）→ `{ok, displayStatus, status|reason}`。
- 调用顺序铁律：查设备+授权 → 注册监听 → 发消息（SyncEngine 已封装，6s 超时）。

## 二、新默认流程设计（手环引导 → APK 激活）

### 2.1 总体链路

```
手环「高级版」页
 └─ 顶部新增推荐卡：【推荐 · 用安卓手机激活】
     ├─ 展示「APK 下载」二维码（https://app-auth.gudq.com/android-apk.html?deviceId=…&c=…&r=…，带追踪）
     └─ 一句话提示：iOS / 鸿蒙暂不支持，请用下方原流程
        ↓
手机浏览器打开下载页 → 下载 APK → 安装（页面给简明安装指引：允许未知来源等）
        ↓
打开 APK「高级版」激活页
 ├─ ① 购买：按钮直达爱发电（Intent 唤起爱发电 App，失败回落浏览器），链接带追踪参数
 ├─ ② 输码：四格输入框（4 位，支持粘贴、自动大写、自动跳格）
 ├─ ③ 连接：检测手环；未连接 → 兑换码暂存本地，连接后自动继续
 ├─ ④ 兑换+写入：/api/activate 换 18 位码 → activate 写入手环
 └─ ⑤ 留痕：本地保存「兑换码 ↔ deviceId ↔ 18位码」映射，激活多个手环互不干扰
        ↓
手环高级版页刷新显示有效期；原「扫码购买 → 扫码兑换 → 手输18位」流程原样保留在下方作兜底
```

网站 `activate.html` 与 `user-guide.html` 同步把「推荐：安卓 App 激活」放到步骤第一位，原网页兑换流程降为备选。

### 2.2 关键设计决策

**D1 · 暂存什么：兑换码 + deviceId 双暂存，18 位码到手里也存**

- 用户输入 4 位码但手环未连 → **先不调服务端**（缺 deviceId 无法兑换），只把兑换码存 `SharedPreferences`（如 `ev_pending_activate`）。连接成功后自动走「兑换 → 写入」。
- 若已换到 18 位码但 `activate` 写入手环失败 → 存 `{redeemCode, deviceId, activationCode}`，下次连接同 deviceId 时直接补写，**不再重打服务端**（虽然幂等，但省一次网络与限流额度）。
- 18 位码与 deviceId 强绑定（确定性生成），存在 APK 私有目录无额外泄露面；换手环 = deviceId 变了 → 本地补写逻辑按 deviceId 匹配，不匹配就丢弃本地码、提示重新兑换（服务端会正确拒绝跨设备）。

**D2 · 多手环（终端可能性）显式确认**

- `get_device_id` 与 `activate` 必须打到**同一台**手环。激活页进入时展示目标手环名（复用 `preferredNode`/`NodeChooser` 选择结果），若检测到多台连接，先弹选择框，选定后再读 deviceId；暂存的 deviceId 与当前连接节点不一致时提示用户确认，防止「码是 A 手环兑换的、写进了 B 手环」（服务端会拒绝，但提前拦掉体验更好）。

**D3 · 购买入口不需要 deviceId 也能用，但带上更好**

- 爱发电跳转链接带上 `deviceId` 与 `c`（渠道）/`r`（版本）追踪参数（与手环二维码同一套参数约定），购买归因与漏斗直接并入现有 `tracking_events` / `visitor_logs` 体系，后台「消息投递」已能区分 `purchase_click` 类型。
- 唤起策略：`Intent(ACTION_VIEW, afdianUrl)` + `Intent.createChooser`；系统有爱发电 App 就进 App，没有就浏览器，**不做** `queryIntentActivities` 探测（Android 11+ 包可见性限制，探测反而多踩坑），让 chooser 兜底即可。

**D4 · 一码多机的正确姿势**

- 「安卓端可以激活多个手环」在现有后端语义下 = **多个兑换码对应多台手环**（一个码只能绑一台）。APK 本地保存映射表（`redeemCode → deviceId → activationCode`）用于展示「哪个码激活了哪台手环」；用户拿已用的码去激活第二台会被服务端明确拒绝，APK 端把报错原文透出（含解绑联系方式），不自行「智能重试」。

**D5 · 手环端改动最小化**

- EV 仓只改 `activation.ux`（或 premium-overlay）：顶部加一张推荐卡 + 下载二维码，**不新增协议、不新增后端字段**。老版本 APK/网页用户完全不受影响；新手环 rpk 发版后才出现推荐卡。
- 原三步流程 DOM 原样下移，作为兜底（iOS/鸿蒙/无安卓机的用户仍走老路）。

## 三、稳定性分析（新流程各环节）

| 环节 | 风险 | 概率/影响 | 缓解 |
|---|---|---|---|
| 扫码下载 APK | 手机相机识码容易（比手环识码大屏清晰）；下载页本身就是现成的 `android-apk.html` | 低 / 低 | 追踪参数已有先例；页面带安装指引（未知来源授权、鸿蒙/iOS 提示） |
| 安装 APK | 未知来源拦截、厂商安全提示（EMUI 尤其烦） | 中 / 中 | 下载页图文指引；本仓已有 EMUI 8 真机实测记录；这步只在「第一次」发生 |
| 购买跳转 | 爱发电 App 未装 / deep link 失效 | 中 / 低 | `createChooser` + 浏览器兜底；爱发电是普通网页支付，浏览器路径本身完整可用 |
| 输入兑换码 | 4 位 [A-Z0-9]，粘贴带空格/小写/全角 | 高频 / 低 | 输入过滤（大写化、去空白、限长 4）+ 四格 UI 自动跳格；服务端 `validateRedeemCode` 兜底 |
| 读取设备ID | 手环未连 / EV 版本过低 / NA fallback | 中 / 中 | 现有 `fallback` 警示已就位；NA 码服务端限额 5 次；新流程增加「未连接 → 暂存等待」把硬失败变软等待 |
| 换码（网络） | 无网 / 限流 429 / 服务端 5xx | 低 / 低 | 明确错误文案 + 可重试；所有失败已进后台漏斗与告警 |
| 写入手环 | 蓝牙瞬断、6s 超时、0 回包 | 中 / 中 | D1 暂存补写；SyncEngine 单 listener + 超时机制现成；写入失败不消耗兑换码（服务端已记账，码还在） |
| 多手环错绑 | 写错目标 | 低 / 中 | D2 显式确认 + 本地 deviceId 匹配校验 |
| 暂存丢失/串号 | 卸载重装清掉 SharedPreferences | 低 / 低 | 无损：18 位码是服务端确定性生成的，重新打开激活页用同码同设备再兑换一次即可取回（复用分支幂等） |

**结论：整条链路没有一个新发明的不可靠环节。** 高风险点（网络、蓝牙、限流）全部落在已有 6 个月实战验证的 `SyncEngine` / `/api/activate` / tracking 体系上；新增的只是「暂存 + 补写」这个纯本地、可随时重来（幂等）的缓冲层。

## 四、安全性分析

1. **不新增信任假设。** 4 位兑换码仍是唯一凭证，校验全在服务端；APK 端不做任何本地「预验证」，伪造无门。兑换码只有 4 位、熵偏低，这是既有事实——靠 IP/设备双限流压制爆破，新流程不放大这一点（暂存的兑换码只在用户自己手机上，不上报、不打日志）。
2. **18 位激活码仍可离线伪造**（已知 TODO，需 EV 端同步升级才可修）。新流程不改变此风险面；反而是「以后加签名」时，手输 18 位的老流程可以顺势退役，改动面更小。
3. **暂存数据敏感度低。** 兑换码/激活码本就与设备绑定、单码单机，且服务端留有全量记录；SharedPreferences 私有目录，不跨应用可见。暂不加密可接受，若要加固，`EncryptedSharedPreferences` 一行替换即可（API 23+，本机最低 26 无兼容问题）。
4. **追踪参数合规。** 下载/购买链接带的是机型、OS 版本、渠道等**设备级**参数，与手环端现有二维码、APK `Analytics` 埋点完全同口径（`docs/apk-tracking-telemetry-spec.md` 白名单 + 限长 + 服务端 `sanitizeDevice`），无个人身份信息，不引入新合规面。
5. **无后台行为。** 激活全程用户显式操作，没有后台自动同步/自动激活，符合项目「不要后台自动做事」的硬底线。

## 五、可操作性 / 边界

- **iOS / 鸿蒙**：interconnect 依赖小米运动健康 + xms-wearable AAR，只支持安卓。下载页与手环推荐卡必须明示「需安卓手机」，避免误购——这是新流程唯一硬性前提，文案要放在推荐卡第一行。
- **版本兼容**：手环推荐卡需发新 rpk；老 rpk 用户仍走原流程（无损）。APK 侧 `get_device_id` 对旧 EV 的「回包不识别」已有降级文案。建议下载页带「最低支持 EV 版本」说明。
- **用户迁移**：不需要任何迁移——新流程只是多了个推荐入口，两类入口共用同一套服务端状态。
- **客服成本**：激活类工单的三大来源（手输 18 位出错、扫码失败、网页打不开）全部被新流程消除或绕开；后台漏斗还能看到「下载了没装 / 装了没买 / 买了没连手环」各步转化，定位流失更准。

---

## 六、结论：值得作为新的默认激活流程

**判定：值得，且应尽快上。** 理由：

1. **收益是「减法」**：把用户手工操作从「扫 2 个码 + 手输 18 位」降到「扫 1 个码 + 输 4 位」，且购买、输入、写入全程在手机大屏完成——这正是激活体验的主瓶颈。
2. **成本是「增量」且全部可复用**：服务端零改动；手环端只加一张推荐卡；安卓端在现有 `FastActivateActivity` 上做 UI 升级 + 暂存补写。
3. **失败模式全部可恢复**：网络/蓝牙失败靠幂等复用分支兜底，暂存丢失靠确定性激活码兜底，没有引入任何「做了就回不去」的状态。
4. **顺手打通产品闭环**：装了 APK 的用户天然获得同步/导出导入/提醒/留言全套服务，把「高级版付费」与「安卓 App」绑成同一个价值主张，也符合 APK 改名「Ev课程表」后「首屏给课表、功能名实相符」的定位。

### 落地清单（按仓）

| 仓 | 改动 |
|---|---|
| `ev-schedule-android`（本仓） | `FastActivateActivity`：四格输入框（粘贴/大写/跳格）；购买按钮（chooser 直达爱发电）；连接状态检测 + 兑换码/激活码暂存（`ev_pending_activate`）；重连自动补写；多手环目标确认；激活记录映射展示 |
| `tom/class/class`（EV，需用户同意后改） | `activation.ux` 顶部推荐卡 + APK 下载二维码（带 deviceId/c/r 追踪）+ iOS/鸿蒙提示；原流程下移保留 |
| `app-auth` | `android-apk.html` 下载页加安装指引与追踪参数承接；`activate.html` / `user-guide.html` 步骤重排（推荐 APK 流程置顶） |

建议实施顺序：先本仓 APK 侧（独立可用、不动别人），再 app-auth 网页（纯展示），最后 EV 仓手环推荐卡（需发版，放最后）。
