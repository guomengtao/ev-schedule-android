# 手机读取手环数据 & 远程管理手环 · 能力边界分析

> 用户 2026-10-05 提问：手机端能拿到多少**手环的数据**？能对**手环做哪些操作 / 管理**？
> 例如 看步数 / 卸载应用 / 管理空间 / 电量 等。**本文只做能力边界分析，不含实现。**
>
> 姊妹文档：`docs/手环遥控手机-能力扩展可行性分析.md`（反方向：手环 → 遥控手机）。

## 一、先把两个方向分开（数据来源完全不同）

| 方向 | 谁发起 | 能力来自哪 | 现状 |
|---|---|---|---|
| **手环 → 遥控手机** | 手环点按钮 | 手机端 App 自己的 Android 权限 | 已落地 A 类（手电筒/天气/导航/单词） |
| **手机 → 读取/管理手环**（本文） | 手机发起 | ① **小米穿戴 SDK**（直读）② **手环端快应用 push**（间接） | 未做 |

关键认知：**"手机读手环"不是一套 API，而是两条完全不同的路子**，能力天差地别 —— 见 §二 / §三。

## 二、路子①：手机端"直读" —— 小米穿戴 SDK（`xms.wearable`）

权威：**《小米穿戴第三方 APP 能力开放接口文档 v1.4》**。本项目手机端 `SyncEngine.java`
已在用同一套 SDK（`com.xiaomi.xms.wearable.*`）。SDK 暴露 5 个 Api：

| API | 方法 | 能干什么 |
|---|---|---|
| `NodeApi` | `getConnectedNodes()` | 查已连接设备 |
| `NodeApi` | **`query(nodeId, DataItem)`** | **状态查询** |
| `NodeApi` | **`subscribe / unsubscribe(nodeId, DataItem)`** | **状态订阅（变化事件）** |
| `NodeApi` | `isWearAppInstalled(nodeId)` | 手环端本应用是否已装 |
| `NodeApi` | `launchWearApp(nodeId, uri)` | 打开手环端应用（**已在用**） |
| `AuthApi` | `checkPermission / requestPermission` | `DEVICE_MANAGER` / `NOTIFY` 两类权限 |
| `MessageApi` | `sendMessage / addListener` | 点对点消息（**已在用**） |
| `NotifyApi` | `sendNotify(nodeId, title, msg)` | 系统通知卡（**已在用**） |
| `ServiceApi` | `registerServiceConnectionListener` | 第三方 App ↔ 小米运动健康 的连接状态 |

### SDK 能直读的 5 种"设备状态"（`DataItem`）

| 状态 | 查询 `query` | 订阅 `subscribe` | 取值 |
|---|---|---|---|
| 连接状态 | ✅ | ✅ | 连接 / 未连接 |
| **电量状态** | ✅ | ❌ **N/A** | **0~100** |
| 充电状态 | ✅ | ✅ | 充电中 / 非充电 / 充满 |
| 佩戴状态 | ✅ | ✅ | 佩戴 / 未佩戴 |
| 睡眠状态 | ✅ | ✅ | 睡眠中 / 清醒 |

> ⚠️ **电量只能"查"不能"订阅"**（文档订阅触发条件为 N/A）——想拿实时电量得自己轮询。

### SDK 拿不到的（重要）
- ❌ **步数 / 心率 / 运动历史等健康数据** —— SDK **完全没有**健康数据接口（只有"佩戴/睡眠"两个粗状态）。
- ❌ **存储空间、设备型号 / 序列号** —— SDK 不提供。
- ❌ **应用列表 / 卸载 / 系统清理** —— SDK 是"通信 SDK"，不是"设备管理 SDK"，无此类 API。

## 三、路子②：手机端"间接拿" —— 手环端快应用 push

手环端快应用**运行在手环上**，能直接调 Vela 系统 API 读自己的家底，再经 interconnect
**主动发给手机** —— 手机就"获得"了这些数据。

**好消息：本项目手环端已经会读这些了** —— 见 `src/pages/device-info/device-info.ux`：

| 已实现读取 | API |
|---|---|
| 型号 / 品牌 / 制造商 / 代号 / 设备类型 | `device.getInfo()` |
| 系统版本 / 平台版本 / API Level | `device.getInfo()` |
| 屏幕宽高 / 密度 / 形状 / 语言 / 地区 | `device.getInfo()` |
| 设备 ID / 序列号 | `device.getDeviceId()` / `device.getSerial()` |
| **总存储空间 / 可用存储空间** | **`device.getTotalStorage()` / `getAvailableStorage()`** |

→ 也就是说：**存储空间、型号、序列号、系统版本这些"手环家底"，手环端本来就读得到，
只差"多写一条 push 把它们发给手机"。** 这是本文最有价值的落地点。

## 四、逐项回答用户举的例子

| 用户问的 | 手机能做到吗 | 怎么做到 | 结论 |
|---|---|---|---|
| **电量** | ✅ **能** | 优先走 SDK `NodeApi.query` 直读（0~100） | 推荐，纯手机侧，零协议改动 |
| **步数** | ❌ **不能** | SDK 无健康 API；手环端 Xiaomi Vela `@system.sensor` **不含计步** | **做不到**（详见 §五） |
| **心率** | ❌ 不能 | 同步数 | 做不到 |
| **存储空间（总/可用）** | ✅ **能** | 手环端 `getTotalStorage/availableStorage` → push 给手机 | 能做，需加一条 push |
| **卸载应用** | ❌ **不能** | 快应用沙箱无权限；SDK 无 API | **做不到**（详见 §五） |
| **管理空间 / 清理** | ⚠️ **只能清自己** | 快应用只能管自己的 `@system.storage`（KV）+ `@system.file`（私有文件） | 只能"清本应用缓存" |
| 连接 / 充电 / 佩戴 / 睡眠状态 | ✅ 能 | SDK `query` / `subscribe` 直读 | 能做 |
| 打开手环应用 / 让手环震动弹提示 | ✅ 能 | `launchWearApp` + 既有消息协议 | **已在用** |

## 五、为什么"卸载应用 / 步数"这两档基本是空的（根因）

1. **Vela 快应用是沙箱**：只能访问**自己的**私有存储 + 有限的系统信息 API；
   没有"应用列表 / 卸载 / 改系统设置 / 读健康库"这类接口 —— 这是**平台安全模型**决定的，不是没写。
2. **穿戴 SDK 是"通信 SDK"**：它的设计目标是"让手机和手环上的应用互相传消息 / 通知"，
   不是"让手机管理手环硬件"。所以只有连通性 + 几个粗状态，**没有硬件管理面**。
   （对照：Apple Watch 第三方同样拿不到"卸载表端 App"的 API，只能由系统 App 管。）
3. **步数实测也拿不到**：Vela `@system.sensor` 官方只有 加速度 / 罗盘 / 气压（且**分母机型**）；
   社区实测（2026-07，小米手环 10）`subscribeStepCounter` 直接 `not a function`，
   隐藏的 `@service.health` 里 `getTodaySteps()` 同样 `not a function` —— **小米自己的实现没开这个口子**。
4. **真正能"管理手环"的只有系统级 App**：**小米运动健康**（有系统特权）。第三方 App 越不过这条线。

## 六、结论：三档

- **A 类 · 建议做（纯读取，低风险，成本低）**
  - **电量**（SDK `query` 直读）；
  - **连接 / 充电 / 佩戴 / 睡眠**四态（SDK `query` + `subscribe`）；
  - **存储空间 + 设备信息面板**（手环端 `device-info` 已有数据 → 加一条 push 给手机）。
- **B 类 · 可做，看机型（需手环端加 push 协议）**
  - 传感器类：加速度 / 气压 / 罗盘 —— **手环 9 标准版只有加速度**；气压/罗盘要 9 Pro / 10 / Watch 系。
- **C 类 · 做不到，别碰（写进文档，免得反复试）**
  - **步数 / 心率等健康数据**（无 API）；
  - **卸载手环应用 / 管理手环系统空间**（无权限）；
  - **读取手环屏幕 / 截屏**（无 API）。

## 七、若决定做，落地建议（本项目）

1. 手机端加一张「手环状态」卡：`NodeApi.query(nodeId, 电量项)` 显示电量 +
   `subscribe` 充电/佩戴变化（电量不可订阅，轮询或进页面时查一次）。
2. 手环端把 `device-info` 已读的**存储/型号/序列号**打包成一条 `sysinfo` push
   （复用既有 interconnect 协议：手环端加 1 个方法 + 手机端加 1 个 unsolicited action，
   **注意总纲：新增手环主动 push 的 action 必须同步加进 `SyncEngine` 白名单**）。
3. **步数/心率明确标记为"平台不支持"**，不做无谓尝试。
