# 课表同步拒绝提示细化-修复方案

## 一、问题定义

用户看到的提示：`手环拒绝了写入：no courses，本地已保留`（变体「本地已经保留」）。

**代码位置**：`apk/src/com/application/watch/classschedule/SyncCoordinator.java` 第 157–159 行，`doMerge()` 的 `onReply` 回调中的「真拒绝」分支。

### 手环端真身（已核实，推翻早期假设）

手环端源码：**`ev/class-schedule/src/app.ux`**（不是 `ev-schedule-sync`，后者是 AstroBox V2 的 Rust 多格式插件，不参与本链路）。

**核实后的真实语义**——`no courses` 有且只有一个判定点：`syncExtractCourses(payload)` 返回 `null`（141–153 行）：

```js
function syncExtractCourses(payload) {
  var list = null
  if (payload && payload.length !== undefined && typeof payload !== "string") list = payload
  else if (payload && payload.courses)                                    list = payload.courses
  else if (payload && payload.schedules && payload.schedules[0] && payload.schedules[0].courses)
                                                                          list = payload.schedules[0].courses
  else if (payload && payload.payload)  return syncExtractCourses(payload.payload)   // 递归
  return (list && list.length) ? list : null     // ← 空数组也返回 null！
}
```

| 真实病因 | 触发条件 | 判定 |
|---|---|---|
| **用户主动清空课表，`courses: []`** | `list.length === 0` → null | ❌ **真 bug**：清空课表这个功能在手环端根本无法完成，还被渲染成「拒绝写入」 |
| 报文字段结构不匹配（未落在上述 4 种形态之一） | list 恒 null | 结构上已兼容 4 种，概率低 |
| 老手环端（pre-P2）遇**其他** action 兜底撞进 import | 见 app.ux 271 行注释 | ⚠️ **不适用于 import 本身**——见下 |

**关键更正**：早期判断「老手环不认识 action 会掉进 import 兜底回 no courses」——**这条对 `import` 这个 action 不成立**。当前源码里 `import` 是**显式白名单路由**（1038 行 `if (parsed.action === "import")`），不是兜底；且 P2 起已收口（1088–1092 行）：

- 完全**无** action → 才走老 import 兼容
- **有** action 但不在白名单 → **安全忽略、不回包**（不会再产生 no courses）

所以「版本过旧」不是本提示的主因，**空课表才是**。

## 二、出现时刻（触发链路）

```
用户触发同步（三个入口）
  ├─ 课程编辑页保存后
  ├─ 课表列表页手动同步
  └─ 首页同步
        ↓
SyncCoordinator.syncNow()
        ↓
  ① export：手机端下拉手环数据
  ② doMerge：三方合并（base / 手环 / 手机）
  ③ 仅当手机端有改动 → 上行 import
        ↓
  手环回包 ok:false → 本提示出现
```

**关键约束**：

- 只有**手机端有改动**才会上行 import，纯拉取手环数据不会走到这条分支
- 落盘先于上行（122 行 `updateCourses` 先落盘），所以「本地已保留」是真话，base 留 dirty 下轮重试
- `SyncEngine` 串行队列同时只有一个在途请求，不存在旧回包误配

**一句话回答用户**：这是你在**手机端改完课表、保存后同步**（或手动点同步）时，手机把改动推给手环、手环回了个失败，才会出现——不是日常自动同步的常态提示。

## 三、修复方案

### 阶段一：手机端文案矩阵（最小改动，字符串层）

改动文件**仅** `SyncCoordinator.java`，`finish()` 调用前按 reason 分派，纯字符串层，不触碰同步状态机。

| reason | 新文案 |
|---|---|
| `no courses` | 手环未收到课程数据（若你刚清空课表，请见下方空课表处理）；本地已保存 |
| `convert empty` | 手环端转换课程数据为空，请检查课程字段是否完整；本地已保存 |
| `read failed` | 手环端读取课表失败，请重启手环 App 后重试；本地已保存 |
| `backup failed` / `write failed` | 手环端写入/备份失败（存储空间可能不足）；本地已保存 |
| 空 reason | 手环拒绝了写入（未返回原因），本地已保存（兜底保留） |

**空课表特判（手机端侧）**：上行 import 前若 `courses.isEmpty()`，提示「已同步空课表（手环端当前无课程）」——需配合手环端阶段二才能真正生效。

### 阶段二：手环端空数组合法化（根治，两侧配合）

**这才是病根所在**，改 `ev/class-schedule/src/app.ux`：

1. `syncExtractCourses` 区分「字段不存在」与「数组为空」两种返回：
   - 字段不存在 → `null`（真错误 → `no courses`）
   - 数组存在但为空 → 返回 `[]`，由 `syncHandleImport` 走**清空分支**
2. `syncHandleImport` 新增：`list.length === 0` → 按 index 写空数组 + 回 `{ok:true, count:0, cleared:true}`（语义：清空课表成功）
3. 手机端收到 `cleared:true` → 提示「已同步空课表」

**为什么必须两侧改**：只改手机端的话，空课表仍然写不进手环（手环直接回 ok:false 拒收），手环上的旧课表不会被清掉——提示变好看了，但功能依然是坏的。

### 阶段三（可选）：版本字段

`buildImport` 加 `version` 字段用于未来协商。**非本次必要**——版本不配已被证实不是本提示主因，优先级低于阶段二。

## 五、验收 checklist

- [ ] 各 reason 提示按矩阵分派，`no courses` 不再泛称「拒绝」
- [ ] **清空课表后同步：手环端课程被真正清空**，手机端提示「已同步空课表」而非失败 ← 核心验收项
- [ ] 正常课表同步不受影响（回归）
- [ ] 手环端 `write/backup failed` 提示含「存储空间」指引
- [ ] 两侧分别编译通过；真机跑一次成功路径 + 一次清空路径

## 六、风险与回滚

- **阶段一**：纯文案，无状态机变更，风险极低，单文件 revert 即可
- **阶段二**：触碰手环端写入路径，需注意——清空分支同样要走 `syncWriteCoursesToIndex` 的「先备份再写」流程（391 行备份键 `astrobox_sync_backup_<index>`），保证可回退
- **注意**：文案改动会影响断言文案的 UI 自动化用例（如有需同步更新）
