# EV 课程表安卓端「课程表」页面 · 多设备强隔离方案

> 日期：2026-10-02 · 状态：**草案（待确认）** · 作者：AI 侦察 + 拟稿
> 关联：`docs/课表套数不一致分析.md`（口径问题）、`docs/aiot-ide-real-device-deviceid-analysis.md`（deviceId 来源）
> 跨端影响：安卓侧 `ev-schedule-android` 为主；手环侧 `ev/class-schedule` 基本不改（见第五节）

---

## 一、需求

- 一个手机可能连**多台手环**（同账号下手环 + 手表，或两台同型号手环）。
- 每台手环各自同步一套/多套课表，**同步后互不串台**：设备 A 的课表绝不覆盖设备 B 的，反之亦然。
- App「课程表」页面（底部导航「课程表」Tab，`ScheduleListActivity`）必须**明确标注每套课表属于哪台设备**，让用户一眼分清。

---

## 二、现状与根因（实证）

### 2.1 好消息：多设备连接链路已经具备

`SyncEngine` 已为多设备做好了底层：

| 能力 | 位置 | 说明 |
|---|---|---|
| 设备选择 | `SyncEngine.java:78-162` `DeviceInfo` / `chooseNode()` / `pendingDevices()` | 发现多台时弹 UI 选，记住选择 |
| 记忆上次选的设备 | `SyncEngine.java:85` `KEY_PREFERRED_NODE` = `"preferred_node"` | 持久化 nodeId |
| 手环真实 ID | `SyncEngine.java:350` `getDeviceId()` 发 `{"action":"get_device_id"}` | 手环回 `deviceId`(32位) / `deviceId4`(后4位) / `fallback` |
| 设备名 | `SyncEngine.java:71` `deviceName` | 连接时拿到，如「小米手环 10 Pro」 |
| 已缓存 | `Stats.cacheWatchDeviceId(ctx, json, nodeId)`（`SyncEngine.java:359`） | 埋点已同时存 `device_id` 与 `node_id` |

手环侧 `ev/class-schedule` 的激活页 `fetchDeviceId()` 调 `@system.device.getDeviceId()`，失败（NA/unknown）时 fallback 到本地 `uuid-<32位>`（`device-uuid.js`，存 `device_uuid_v1`）。即 **deviceId 是稳定的**（真实硬件 ID 或持久化 UUID），且已有兜底。

### 2.2 坏消息：课表主键没有设备维度（这就是 bug 根因）

`ScheduleStore` 里 sync 课表的主键规则（`ScheduleStore.java:180`、`239`）：

```java
// upsertFromWatch：手环同步回一套课表
String id = "ev_watch_" + name;          // ← 仅用「课表名」做去重键，无设备！
// markSynced：本机课表上传到手环后改身份
String newId = "ev_watch_" + s.name;     // ← 同样无设备
```

后果（多设备必现）：
- 设备 A、B 上都有叫「我的课表」的课表 → 同步回来是**同一个 id** → 后者覆盖前者，强隔离彻底失效。
- `ScheduleListActivity.render()`（`ScheduleListActivity.java:164`、`171`）用
  `ScheduleStore.find(this, "ev_watch_" + bandNames[i])` 匹配本地——`bandNames` 是**当前连接设备**的清单。换连设备 B 时，会用「B 的课表名」去匹配「A 存下来的同名课表」，误判为「本地已存」，渲染串台。
- `Schedule.sub()`（`ScheduleStore.java:62-69`）副行只有「来自手环 · N门课 · 最后同步 xxx」——**完全没有设备标识**，页面上根本分不清属于哪台手环。

### 2.3 结论

连接层（谁连哪台）已有，但**课表数据层（哪套课表属于哪台）是空白**。强隔离 = 给数据层补上设备维度，并以「设备 × 课表名」作为唯一路由键。

## 三、设计

### 3.1 设备标识选型：`deviceId` 优于 `nodeId`

| 候选 | 稳定性 | 结论 |
|---|---|---|
| `deviceId`（手环真实/UUID 兜底，32位） | 稳定，换机/重连不变 | ✅ **隔离键用这个** |
| `nodeId`（BLE 节点 id） | 可能随重连/重配对变化 | ❌ 仅做路由辅助，不作主键 |

- 内部键用完整 `deviceId`（保证唯一）。
- 显示用 `deviceName` + `deviceId` 后 4 位掩码（如「小米手环10 Pro · ··3f2a」），因为同型号设备 `deviceName` 会重名。

### 3.2 数据模型变更（`ScheduleStore.Schedule`）

新增两个字段：

```java
public String deviceId = "";     // 归属手环的真实 ID（sync 课表必有；local 课表为空）
public String deviceName = "";   // 归属手环展示名（同步时缓存）
```

老 id 规则 `ev_watch_<name>` 升级为**二元组路由键**：

```java
// sync 课表 id（唯一：设备 × 课表名）
String id = "ev_watch_" + deviceId + "::" + name;
// 去重判据也改为 (deviceId, name) 同时相等才算同一套
```

`local` 课表仍用 `ev_local_<timestamp>`，`deviceId` 留空（本机课表不与任何手环绑定）。

### 3.3 同步路由（强隔离的核心）

**同步进（手环 → 手机）`upsertFromWatch(c, watchName, dayGrouped)`**
- 入参补 `deviceId` / `deviceName`（取自 `SyncEngine.currentDeviceId()`）。
- 用 `ev_watch_<deviceId>::<watchName>` 定位，**只写这一台设备的这份**，绝不碰别的设备。
- 激活跟随策略加设备约束（防串台，见 3.5）。

**同步出（手机 → 手环）`syncToWatch` / `markSynced`**
- 发出 `import` 消息时，目标就是**当前连接设备**（路由天然由 BLE 连接决定）。
- `markSynced` 改身份时也用 `ev_watch_<deviceId>::<name>`，并补全 `deviceId`。

**`ScheduleStore.find` / `list`**：所有调用方（列表、激活、三方合并）改为按新 id 或 `(deviceId,name)` 检索，不再用裸名字。

### 3.4 UI 分组与标注（`ScheduleListActivity`）

- **按设备物理分组**：顶层标题从「手环课表 / 本机课表」改为「设备A（型号·后4位）」一组、「设备B」一组、「本机课表」一组。每组内再区分该设备的 sync 课表与 local 课表。
- **卡片副行** `sub()` 改为包含设备：`来自 小米手环10 Pro··3f2a · 8门课 · 最后同步 3分钟前`；本机课表仍是「仅本机」。
- **「当前」勾选**：全局仍只有一个激活课表（供首页/插件/提醒），但卡片上明确标出它属于哪台设备。
- **「手环上共 N 套」统计**：原逻辑按当前连接设备的 `bandScheduleNames` 匹配本地名（`ScheduleListActivity.java:168-169`）——改为按 `deviceId` 匹配，避免跨设备误数。

### 3.5 激活策略（防"同步晃一下就换台"）

现有逻辑（`ScheduleStore.java:197-199`）：当前激活的是 sync 课表时，任意新同步都跟随激活。
**加设备约束**：只有「当前连接的设备」同步回来的课表才允许跟随激活；其他设备的同步只更新数据、不抢激活。
理由：多设备用户可能长期让设备 B 连着，设备 A 偶尔同步一次——不能让 A 的一闪把 B 当前的课表换掉。

### 3.6 数据迁移（老用户无设备维度数据）

老数据结构 `ev_watch_<name>`，升级时 `deviceId` 未知。策略：
1. 首次打开（在 `ensureInitialized` 或一次性迁移标记下）：
   - 在线且拿到 `deviceId` → 把现有 `ev_watch_<name>` 重写为 `ev_watch_<deviceId>::<name>`，并填 `deviceName`。
   - 离线 / 拿不到 → 标记为 `deviceId = "legacy-unknown"`，显示「未知设备（升级前）」，连接任一设备同步后即自然归到该设备（dup 按新键处理，旧 legacy 记录可保留或提示合并）。
2. 迁移不可逆但安全：`upsert` 以新 id 为主键，旧 id 记录作为孤立项，用户可在 UI 删除。
3. **绝不**用 `ev_watch_<name>` 去匹配新设备清单（这是旧 bug），统一走 `(deviceId,name)`。

### 3.7 手环侧影响（基本为零）

- 手环本地课表是按「名称」管理的**单机数据**，多设备隔离完全发生在安卓侧：安卓把「设备A的课表」与「设备B的课表」存成两份独立 `Schedule`，分别 `import` 回各自连接的设备（BLE 路由自然分开）。
- 手环 `import` 处理按 `scheduleName` 覆盖自身课表，现有逻辑无需改。
- **唯一建议**（非必须）：手环 `import` 响应可选回 `deviceId` 回执，便于安卓确认「确实写到了这台」；但安卓已有 `getDeviceId` 可独立校验，不做也行。

## 五、兼容与风险

- **老客户端**：只加字段，老 JSON 缺 `deviceId` 按 `legacy-unknown` 兼容（§3.6）。不删不改旧键语义。
- **手环版本**：`get_device_id` 需要手环 EV 足够新；老版本回包 `ok=false` 时 `deviceId` 取不到 → 退化为 `nodeId`+`fallback` 标记，仍隔离（仅换机/重连可能漂移，可接受）。
- **同型号重名设备**：靠 `deviceId` 内部区分、`deviceName+后4位`显示区分，已覆盖。
- **激活语义变更**：§3.5 的"只跟随当前连接设备"是行为微调，需在方案确认时和用户对齐（多设备用户是否希望"连哪台就显示哪台"）。

## 七、验证标准（真机）

1. **强隔离**：连设备A同步「我的课表」→ 切连设备B同步同名「我的课表」→ 回设备A页面，A 的课表内容**未被 B 覆盖**（两设备各一份）。
2. **页面区分**：课程表页按设备分组，卡片副行显示设备名 + 后4位，无歧义。
3. **离线可用**：断开所有手环，两份课表都可独立查看/切换/本地编辑。
4. **老数据**：升级前有课表的用户，升级后课程不丢；连上设备后归属正确（或显示"未知设备"待归并）。
5. **激活不抢位**：设备B常连时，偶发同步设备A不会把首页/插件课表换成 A 的。

## 八、待确认项（实施前需用户拍板）

1. **全局单一激活 vs 每设备独立激活**：本方案选「全局单一激活 + 每套课表标注设备」（实现简单、插件/提醒零改动）。若需要「每台手环独立显示各自当前课表」，需改 `CourseCache` 与插件，工作量大很多。
2. **设备名显示格式**：`deviceName + 后4位` 是否足够？要不要允许用户给设备起别名（昵称，类似 `setNickname`）。
3. **手环侧是否顺带加 `import` 回执 deviceId**：建议不做（安卓侧已可校验）。
4. **老数据 `legacy-unknown` 是否提示用户合并**：默认保留可删，不自动合并（避免误吞）。

> 确认后开始 P1。跨端状态（手环侧 0 改动 / 安卓侧 4 阶段）请登记到 `PROJECT-MAP.md` 协作状态表。
