## 1. 一句话结论

> 这不是「页面太空」，而是**三张并列的卡在争主角，而真正的主角（四格兑换码）排在第三位**；
> 同时**同一件事（连没连上手环）被三个地方各说了一遍**，反馈又散在两个通道里。

本页的真实用户只有两种：

- **A｜已付款、拿着 4 位码来激活的** —— 绝大多数，其中一部分还是从爱发电点深链直接跳进来的（一进来就该看到输入框）。
- **B｜还没付款、来看怎么买的** —— 少数，且看到「怎么买」之后就要立刻能买。

现状把 **B 的需求（买码卡）放在 A 的需求（输入卡）前面**，对 A 型用户来说，每次进来第一屏都是「一个自己已经完成过的步骤」。

## 3. 诊断

| # | 问题 | 证据（代码位置） | 为什么致命 |
|---|---|---|---|
| **H1** | **步骤编号断裂** | 全页只有 `"① 购买兑换码"`(`:98`) 与 `"② 输入 4 位兑换码"`(`:129`) 两个编号，中间夹着一张无编号的设备卡(`:110`) | 实际流程是「买码 → 读设备 → 输码 → 激活」**4 步**。编号给出 ①② 却让第 2 步缺席，读序变成「① 购买 → ？设备 → ② 输入」——编号不但没帮忙，反而**暴露了一个不存在的空洞** |
| **H2** | **同一件事说三遍**（三状态源） | `ConnectionBar.attach`(`:93`) + `deviceView`(`:475` "设备ID：（未连接手环）") + `statusView`(`:476` "请先回首页完成连接（需要小米运动健康）") | 未连接时**三条同时说「没连上手环」**，措辞各异。用户不知道信谁，也不知道该点哪一条。与前几期反复出现的 H1 同型 |
| **H3** | **主次颠倒：买码卡占首屏第一顺位** | 卡①(`:97`) 在卡③(`:128`) 之前 | 来激活的用户第一步永远是「滚过一张自己已经用过的卡」。深链直达的用户更是如此 |
| **H4** | **`resultView` 是「三合一」裸文本，且反馈通道有两个** | `resultView`(`:142`) 同时承担：深链提示(`:201`)、呼叫手环反馈(`:264`/`:275`)、激活全过程(`:558`/`663`/`:680`…)。而「呼叫手环」的成功反馈写的是 `statusView`(`:275` vs `:667`) | 一页两套反馈通道，同一动作的反馈出现在两个位置。**设置页 v0.5.152 刚刚确立「反馈就地化」原则，本页是唯一还没执行的一页** |
| **H5** | **两个不同级别的低频动作同级并列** | `[重新读取设备ID]`(`:117`) 与 `[呼叫手环（响铃找表）]`(`:121`) 都是全宽次按钮 | 一个是「刷新数据」、一个是「表找不到了」的排障动作，语义不同级、频次都极低，却让设备卡高达约 **200dp**，成为页面上最占地方的一块 |
| **H6** | **两段工程师味等宽说明** | `Ui.mono(...)`(`:146`)：「前置条件：/ 说明：」共 7 行、10.5f 无行高 | **硬前提「手机已安装小米运动健康」被埋在最底部**——用户失败时才知道要装。且 mono 等宽字体与全站设计语言不搭（设置页已删同款） |
| **H7** | **字号越界：第 9 档** | `b.setTextSize(24f)`(`:328`) | **24 不在 7 档字号内**（22/17/15/13/11.5/10.5）。继设置页 `13.5f` 之后又一档越界。而本页四格是本页唯一核心控件，越界的正是最该守规矩的地方 |
| **H8** | **四格视觉权重不足，且没有聚焦指示** | `cell.setBackgroundDrawable(Ui.round(Ui.CARD2, 10, 1, this))`(`:317`) | 四格是**本页主角**，却用与卡面同族的 `CARD2` + 1dp `LINE` 描边 → 看起来像「四个灰格子」。且**四格外观完全一致，看不出焦点在哪一格**（自动跳格后尤其明显） |
| **H9** | **同一件事说三遍（文案层）** | 副标题「一键激活：**只需填 4 位**兑换码」(`:91`) + 「**② 输入 4 位**兑换码」(`:129`) + 「支持长按粘贴，**自动大写**」(`:133`) | 「4 位」说两遍；而「自动大写」是**用户不需要知道**的实现细节，真正有用的信息只有「支持粘贴」一条 |
| **H10** | **成功态没有「成功的样子」** | 成功只在 `resultView`(`:663`) 与 `statusView`(`:667`) 各写一行绿字 | 这是**用户付完钱跑完整个流程的终点**，一个付费转化页最关键的一屏只有一行 12.5sp 小绿字。用户成功后会愣住：「然后呢？」 |
| **H11** | **深链自动激活过程不可见** | `handleDeepLink`(`:201`) 把提示写进同一个 `resultView` | 深链用户从爱发电点进来时，"正在自动激活"这一**最需要信任感的时刻**，被塞进了和报错同一个灰度文本里 |

## 4. 设计原则

| # | 原则 | 说明 |
|---|---|---|
| **P1** | **主角只有一个** | 本页唯一核心动作是「填 4 位码 → 一键激活」。它必须占据**首屏第一屏、最容易被拇指够到**的位置 |
| **P2** | **同一事实只在一处说** | 连接状态、设备 ID、激活进度，各自**唯一归属地**；其余位置只引用不重复 |
| **P3** | **反馈就地化** | 谁的按钮，反馈就在谁身上（按钮自反馈 / 该行副文案），**页面上不再有独立的反馈通道** |
| **P4** | **单路径任务不用编号** | 编号是给「可乱序的并列步骤」用的。本页是线性单路径，用**视觉层级**（主卡 / 次卡）表达主次即可 |
| **P5** | **硬前提前置到需要它的地方** | 「需装小米运动健康」放到**未连接态就地出现**，而不是页面最底部的等宽说明里 |
| **P6** | **越界字号归零** | 本页顺带消除 `24f`，回到 7 档内（`SP_DISPLAY 22f`） |

## 5. 决策

| # | 决策 | 解决 | 依据 |
|---|---|---|---|
| **D1** | **删掉顶栏副标题**「一键激活：只需填 4 位兑换码」 | H9 | P2 / P4 |
| **D2** | **删 `ConnectionBar`**，设备状态收敛为**唯一「设备行」**（放在输入卡顶部） | H2 | 首页 / 课表库 / 手环页均已删或改造过同一组件，本页沿用同一处理 |
| **D3** | **输入卡提为首屏第一张卡**，购买入口降为输入卡下方的**次级入口行** | H3 | P1 |
| **D4** | **取消 ①② 编号**，改用「主卡（白）+ 次卡（弱）」的视觉层级 | H1 | P4 |
| **D5** | **四格视觉强化**：`CARD` 白底 + **2dp 描边**（未聚焦 `LINE` / 聚焦 `ACCENT`）；字号 `24f → SP_DISPLAY 22f`；高度 54 → **56dp**；格间距 10 → **8dp**（落 4dp 栅格） | H7 H8 | P6；尺寸校验：屏宽 360dp − 页面 40 − 卡内 28 = **292dp** 可用，四格 4×56 + 3×8 = **248dp**，余量 44dp |
| **D6** | **反馈就地化**：删 `resultView`；「一键激活」→ **按钮自反馈**（激活中… → 已激活 ✓）+ 卡内**结果条**；「呼叫手环」→ **该行文案自反馈**；深链提示 → 卡内**顶部提示条**（`ACCENT`） | H4 H11 | P3，与设置页 v0.5.152 同款做法 |
| **D7** | **设备行收编两个低频动作**：「重新读取设备ID」「呼叫手环」→ 行右侧 **⋯** 弹层；**未连接态下整个 ⋯ 隐藏** —— 这两个动作都依赖连接（`ringBand()` 在 `hasNode()==false` 时必然失败），把**不可执行的动作**摆成按钮 = 引导用户去撞墙。此时唯一正确的动作是引导卡里的「去首页连接」（见 §11 修正 ①） | H5 | 复用课表库 / 手环页的 ⋯ 模式 |
| **D8** | **`Ui.mono` 两段说明拆解**：硬前提（需装小米运动健康 / 需已连接）就地写进**未连接态的引导卡**；其余（iOS 暂不支持 / 一码一台 / 换手机不用重激活）→ 顶栏 **⋯ → 常见问题**底部弹层。**删掉等宽字体** | H6 | P5 |
| **D9** | **购买入口重做**：输入卡下方一行设置行式入口 —— `还没有兑换码？前往爱发电购买 ›`（正文 `SP_BODY`，链接词 `ACCENT`），保留「4 位码 / 大写字母或数字」一句话副文案 | H3 H9 | P1：主按钮位置必须留给「一键激活」 |
| **D10** | **成功态独立成卡**：替换输入卡 —— 48dp `OK_LIGHT` 圆底 + `OK` 色 ✓ + 「激活成功」(`SP_TITLE`) + 有效期副文案 + 主按钮「回首页」 | H10 | 付费转化页的终点必须有明确出口（**本方案唯一一处新增行为**，见 R3） |

## 9. 风险与取舍

| # | 风险 / 取舍 | 说明 |
|---|---|---|
| **R1** | `wrapWithBottomBar(.., 2)` 让底栏高亮「手环」tab | 本页是**从设置页进入的子页**（有返回键），高亮「手环」与来源不符。但 `Ui.bottomBar` 的 `current` 无「不高亮」取值，改动会波及 `Ui.java` → **列为观察项，本轮不动** |
| **R2** | `Ui.header` 内部写死 18f、`Ui.title` 19f，均不在 7 档 | **全局遗留**，涉及所有子页面，不属本页范围 |
| **R3** | **成功卡新增「回首页」按钮 = 唯一一处新增行为** | 若坚持「纯视图改动」，可退化为成功卡只展示文案（不新增跳转）。**建议保留按钮**——转化终点需要出口 |
| **R4** | ⋯ 弹层 / 常见问题弹层用 `AlertDialog` | 样式随系统主题，与设置页「提前时间」单选弹层同款做法，零新增组件、零主题风险 |
| **R5** | 深色主题下四格聚焦描边对比 | 浅色 `ACCENT` #2F6BFF 在白底、深色 #5B9BFF 在 #151C30 上均需实机核对（验收 8） |

## 11. v1 落地修正（施工时发现方案本身的 3 处错误）

> 本节写于落地阶段。原方案（§5 / §7）与原型 HTML **未改动**，以本节为准 —— 保留错误痕迹便于回溯「为什么当初会这么想」。

### ① 未连接态「呼叫手环提为行内主按钮」是错的（原 D7 的例外条款）

`callBand()`（`:262`）第一句就是 `if (!SyncEngine.get(this).hasNode()) { 提示「手环未连接，无法呼叫」; return; }`。
**未连接时点它必然失败** —— 把它提为按钮等于让用户点一个注定报错的东西。

> **修正**：未连接态下设备行 **⋯ 整体隐藏**（里面两个动作都不可执行）；此时唯一正确动作是引导卡里的「去首页连接」。
> 已连接时才显示 ⋯，内含 重新读取设备ID / 呼叫手环。

**教训（已写进技能）**：设计「某状态下的快捷动作」时，**先问这个动作在该状态下是否可执行** —— 不可执行的动作永远不该被提为按钮。

### ② 未连接态「输入卡置灰」是错的（原 §7 批次 3）

原方案写「未连接态：输入卡置灰」。但 `activate()`（`:542`）在未连接时会**暂存兑换码**、连上后自动继续 ——
置灰等于否定了自家逻辑，且与「先填码也行」的引导文案自相矛盾。

> **修正**：四格**保持可用**，按钮文案从「一键激活」变为 **「暂存兑换码」**，把暂存能力说出来。

### ③ 「常见问题」原计划两处入口，收敛为一处

原型里顶栏 ⋯ 与设备行 ⋯ 都画了「常见问题」。同一入口两处出现会让用户猜测两者是否不同。

> **修正**：**FAQ 只挂顶栏 ⋯**（全局信息）；**设备行 ⋯ 只放 2 个设备动作**。职责边界：顶栏＝关于本页，设备行＝对设备做什么。
