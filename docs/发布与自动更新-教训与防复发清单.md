## 二、四个根因（每个独立成立，都已处理或对策）

### 根因 1【代码】：升级安装用了泛化 Intent（已在 v0.5.160 修复）

```
旧：Intent(ACTION_VIEW) + setDataAndType(content://…, "application/vnd.android.package-archive")
新：Intent(ACTION_INSTALL_PACKAGE) + setData(uri)
```

- `ACTION_VIEW` 是"用某 App 打开文件"的**泛化意图**，第三方文件类 App（WPS、文件管理器等）可抢注处理器；
- 在华为 BLN_AL20（EMUI）+ 装 WPS 的组合上实测必然被抢；且用户卸载 WPS 后连系统安装器都唤不起 → 该机型上旧客户端安装链路整体失效；
- **修复**：`UpdateChecker.install()` 改用 `ACTION_INSTALL_PACKAGE`（只有系统安装器响应，机制上杜绝被抢），`ACTION_VIEW` 降级为兜底（`988c5ea`）。

> **教训**：处理"系统级动作"（安装 / 拨号 / 发邮件 / 打开网页）时，**必须用专向 action，不要用泛化 `ACTION_VIEW`**——泛化意图的解析结果取决于用户手机装了什么，你控制不了。

### 根因 2【流程】：发布缺「清单同步」强制环节（v0.5.121 孤儿发布）

- GitHub Release 与升级清单**在两个仓库**（Release 在本仓库、清单在 `app-auth/ev/update-<variant>.json`），靠人记就会出现"Release 发了、清单没动"；
- **后果不是"没提醒"那么简单**：清单不同步 = 该版本对所有用户**不存在**，发布等于白发；
- **已固化流程**（详见 §三 checklist）：`bash build.sh` → `gh release create` → **`gh api PUT` 清单**（文档明确：app-auth 必须用 `gh api PUT`，git push 会被并行会话覆盖丢失）→ `curl` 验证。

> **教训**：跨仓库的发布链路，每一跳都要有**机器可验证的检查点**（curl 状态码），不能靠"我记得发过了"。

### 根因 3【认知】：修复永远到不了"已经装坏的旧客户端"

- 鸡生蛋：修复在 0.5.160 里，但**把 0.5.160 装进手机的那一步**是旧代码（0.5.157）在执行——旧代码的安装路径是坏的；
- 服务器端（包、清单、URL）**改任何东西都够不到**已经编译进用户手机的那几行；
- **可行缓解**（本次已用）：
  1. `updateLog` 写**自救指引**——它是唯一能实时改、能精准到达每个用户的通道（已加：「弹出选择打开方式时选软件包安装程序 / Package Installer」）；
  2. 一次性跳板：浏览器下载 Release 页 APK 安装 / 选「软件包安装程序」/ 连电脑 adb 装；
  3. 跳过去之后**永久痊愈**（0.5.160 → 0.5.161 应用内升级实测直接弹系统安装页）。

> **教训**：**评估一个客户端 bug 的严重度时，必须先问"这个 bug 会不会堵死用户升级的路"**——会的话它就是最高优先级，因为它连"修复自己"的通道一起堵死。

### 根因 4【环境】：安全护栏与 adb 掉线（当天反复消耗时间）

- **批量删除护栏**（`SAFE_DELETE_BULK_CONFIRM_REQUIRED`，阈值 500 文件）两次中断构建/发布：
  - `ev/ev-schedule-android/apk/out`（571 文件）→ 构建前必须清；
  - `ev/.temp_class-schedule`（1072 文件）→ `aiot release` 收尾清临时目录被拦 → **退出码非 0 → `&&` 短路 → `rename-rpk.js` 没跑 → 渠道包缺失**；
  - 对策：构建/发布前 `find <目录> -type f -delete`；**根因修复待办**：把这两个纯产物目录加入护栏白名单；
- **adb 掉线**：adb server 被外部重启 / USB 断开，手机当天失联两次；对策：`adb kill-server && adb start-server` → 仍不行拔插 USB；**所有命令带 `-s <SN>`**（防误装到手环模拟器）；
- **并行会话**：版本号被并行构建跳号（0.5.158 被并行会话吃掉）、手环端版本被推进到 1.7.103——发布前必须核对 `version.env` 与 dist 最新产物的对应关系。

## 三、发布 Checklist（以后每次发版照抄）

**发布前**
- [ ] `git status` 干净（无未提交的已跟踪源码）
- [ ] 核对 `apk/version.env` 与 `dist/` 最新产物：**version.env = 下一次构建号，产物比它小一档**；对不上先查并行会话
- [ ] `UPDATE_LOG` 已写：用户视角文案；**若本版修的是"升级/安装"本身，必须写自救指引**
- [ ] 清 `apk/out`（`find out -type f -delete`）

**发布中**
- [ ] `JAVA8_HOME=<zulu-8> JRE_HOME=<jdk-22> UPDATE_LOG="…" bash build.sh`
- [ ] `gh release create v<版本> apk/dist/EVSyncProbe-v<版本>.apk --title "Ev课程表同步器 v<版本>" --notes …`
- [ ] `gh api -X PUT …/app-auth/contents/ev/update-<variant>.json`（带 sha 防并发覆盖；**禁止 git push**）

**发布后（缺一不可）**
- [ ] `curl https://app-auth.gudq.com/ev/update-<variant>.json` = 新版本号
- [ ] `curl -L` 下载双链至少一条 200（镜像 ghproxy 优先，GitHub 直连可能被本机网络挡）
- [ ] **测试机走一次应用内升级全程**（唯一能证明"用户真的能升上来"的办法）
- [ ] PROJECT-MAP 认领行闭环 + `version.env` 基线提交

## 五、一句话版（贴墙上）

1. **系统级动作用专向 Intent**，别用 `ACTION_VIEW`。
2. **发布 ≠ 建 Release**：清单不同步，等于没发布。
3. **修 bug 前先问：这个 bug 挡不挡用户升级的路**——挡的话它是 P0。
4. **updateLog 是唯一能实时触达用户的通道**，要写用户能照做的动作，不是写给自己看的 changelog。
5. **跨仓库发布必须有 curl 级检查点**，并防并行会话（gh api PUT + 版本基线核对）。
