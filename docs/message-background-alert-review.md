# 留言「后台轮询提醒」可行性 / 隐患 / 性能 核实

> 问题：手机端能否在后台经常监控新留言，收到就响铃 + 震动？
> 日期：2026-09-27
> 结论先行：**可行，但有三条硬前提、四个必踩的坑、以及一个"其实不必轮询"的更优解**。

---

## 〇、结论速览

| 维度 | 结论 |
|---|---|
| 技术可行性 | ✅ 可行（**前提：EV 新增 `pull_messages`**，目前还没做） |
| 实时性 | ❌ 做不到"实时"；轮询只能做到"分钟级延迟" |
| 进程被杀后 | ❌ 完全收不到（无推送通道，这是物理限制） |
| 主要隐患 | ⚠️ **重复提醒**（缺 id）、**自己发的留言提醒自己**（缺 from 过滤）、**双重提醒**（手环已震动） |
| 性能开销 | 中等；**关键在频率**——1 分钟一次是浪费，3~5 分钟足够 |
| 更优解 | **让 EV 主动 push**（`chatBridge.send`）为主，轮询只作兜底；频率可降到 15 分钟甚至更低 |

## 一、现状盘点（哪些已经有了）

| 能力 | 状态 | 位置 |
|---|---|---|
| 手机 → 手环 留言（下行） | ✅ 已实现 | EV `app.ux` `syncHandleChatIncoming`：存 `ev_chat_inbox` + 长震动 + 回 `chat_ack` |
| 手环 → 手机 主动发 | ✅ 有桥但未验证 | EV `src/data/chat-bridge.js`（`register(connect)` + `send(text)`）；`initSyncReceiver()` 里已注册 |

| 手机端前台服务 | ❌ 未实现 | — |

> ⚠️ 所以"后台轮询提醒"目前**差一整块**：EV 的拉取接口 + APK 的前台服务与轮询逻辑。

## 二、必要性核实：真的需要"轮询"吗？

这是最值得先想清楚的一点。

**链路的两种触发方式：**

1. **EV 主动 push**（`chatBridge.send`）
   - EV 只有在**自己跑起来**时才能 push（`connect` 是 `initSyncReceiver()` 里拿到的）。
   - 但"手环端产生新留言"这件事，本身就只发生在**用户正在手环上操作 EV** 的时候 —— 那时 EV 一定在前台/常驻，`connect` 一定就绪 → **可以直接 push 给手机**。
   - 手机端只要**进程存活**就能在 Binder 回调里收到，然后提示。
2. **手机主动 pull**（轮询）
   - 用于**兜底**：手机当时不在（进程被杀/断连）→ 漏掉那条 push，下次拉取补回来。

**结论：轮询不是主通道，是补漏通道。** 因此：
- 不必高频（1 分钟一次毫无意义）；
- 合理设计是：**push 实时 + pull 兜底（低频）**；
- 真正决定"能不能提醒"的是**手机进程是否存活**，而不是轮询频率。

## 三、必须先解决的三个硬前提

### 前提 1：EV 新增 `pull_messages`

```
手机 → 手环   {"action":"pull_messages","since":<ts>}
手环 → 手机   {"ok":true,"action":"pull_messages",
               "messages":[{"id":"...","from":"watch|phone","text":"...","ts":...}]}
```
EV 读现有 `ev_chat_inbox`（`src/data/storage-tables.js` 已登记该表）按 `since` 过滤返回。
**改进建议：顺手给每条消息加稳定 `id`**（现在是 `{from,text,ts}`，没有 id → 见坑 1）。

### 前提 2：APK 侧前台服务

- Android 8+ 必须 `startForeground()` + 常驻通知；
- Android 14（本 APK `targetSdk 34`）需 `foregroundServiceType="dataSync"` + `FOREGROUND_SERVICE_DATA_SYNC` 权限，另需 `POST_NOTIFICATIONS`（13+）；
- 已有 `VIBRATE`；`INTERNET` 与埋点一起加过了。

### 前提 3：手环侧要"醒着"

EV 靠 `@system.resident` 保活（`app.ux` 里 `startResident()` 起了"课程表后台运行中"）；息屏久 / 内存压力大会被回收。被回收后**拉取会超时**，必须静默重试而不是弹错。

## 四、四个必踩的坑（隐患）

### 坑 1：重复提醒（**缺 id**）— 最严重

`ev_chat_inbox` 存的是 `{from, text, ts}`，**没有唯一 id**。轮询每次返回同一批消息，APK 无法判断"这条提醒过没有" → **每条都会被反复响铃**。

- 解法 A（推荐）：EV 给每条消息加 `id`（`"m" + ts + rand`），APK 只提醒 id 集合里的新值；
- 解法 B（兜底）：APK 用 `ts + text` 的 hash 去重 —— 同秒同文的重复留言会误判，不如 A。

### 坑 2：把自己发的留言提醒自己

inbox 里手机的留言标记是 `from: "phone"`。手环侧只应提醒 `from == "watch"` 的条目；否则手机每轮询一次就把自己刚发的话提醒一遍。

### 坑 3：双重提醒（手环已经震过了）

用户在手环上看到/被震动提醒过一次，手机再响一次铃 + 震一次 → **打扰翻倍**。

- 建议：手机端默认**只更新未读角标 + 静默入库**；响铃/震动做成**开关**，且默认关闭"手机响铃"（或只在手机前台时响）。

### 坑 4：后台被杀 = 全聋

MIUI/HyperOS 等 ROM 的省电策略会杀前台服务；被杀期间**没有任何通道能唤醒 App**（小米运动健康不提供推送）。用户会形成错误预期。

- 必须做：**引导加入省电白名单 / 自启动**，并在 UI 恒显"上次同步时间"。

## 五、性能评估（含具体量级）

| 项 | 评估 |
|---|---|
| 单次轮询成本 | 1 次 Binder IPC（APK→小米运动健康） + 1 次 BLE 往返（→手环） + EV 一次 `@system.storage.get`；量级 **几十 ~ 几百毫秒** |
| 频率 vs 次数/天 | 1 min → **1440**；3 min → 480；5 min → 288；15 min → 96 |
| 手机耗电 | 单次不多，但**高频会阻止 BLE/系统进低功耗态**；前台服务常驻本身也有开销（几 MB 内存 + 常驻通知） |
| 手环耗电 | 每次被唤醒都要读存储 + 回包，**手环电池更敏感**；高频轮询会明显缩短续航 |
| 建议频率 | **默认 5 分钟**；息屏/静置可降到 10~15 分钟；刚收到消息后的 1~2 分钟内可临时提高（自适应） |
| 不推荐 | < 1 分钟（收益趋零、耗电明显） |

**自适应建议**：以"最近一次成功收到消息"为锚，30 分钟内加密、更久则降频；连续失败则退避（5→10→20 分钟封顶），避免断连时反复空转。

## 六、推荐落地方案（分阶段，每阶段可单独验收）

| 阶段 | 做什么 | 验收 |
|---|---|---|
| **P0** | EV 加 `pull_messages`（**带 id**）；APK 在**前台/打开 App 时**拉一次，只更新未读、不响铃 | 打开 App 能看到离线期间的留言，且不重复提醒 |
| **P1** | APK 前台服务 + 5 分钟轮询（失败退避）+ 通知（声音/震动**默认关**，可开关） | 进程存活时，息屏后 5 分钟内能收到提示 |
| **P2** | EV 侧 push 打通（验证 `chatBridge.send` 真能被手机收到）+ 自适应频率 + 省电白名单引导页 | 手环上发一条，手机在后台能即时提示 |

> P2 的 push 通道若能验证成立，**轮询可以退化为纯粹的兜底**（15 分钟甚至只在唤醒/打开 App 时跑），耗电与打扰都最优。

---

## 七、一句话总结

> **能做，但别指望"实时"；而且要小心别把"提醒"做成"骚扰"。**
> 先补 EV 的 `pull_messages`（务必带 id）、过滤 `from=phone`、手机端默认静默；
> 轮询频率 5 分钟起步并做退避；真正的实时靠 EV 主动 push，轮询只当补漏。

---

## 八、补充核实：手环侧其实没有「给手机的留言箱」

核查 `tom/class/class/src`：`ev_chat_inbox` **只被 `syncHandleChatIncoming`（手机 → 手环）写入**，没有任何"手环 → 手机"的写入方。

结论：

- **手机去轮询 `ev_chat_inbox`，只会拉到"手机自己发出去的话"** —— 既无用，又会造成重复提醒；
- "手环 → 手机"目前**只有实时 push 一条路**（用户在手表上操作时 `chatBridge.send`）；
- 所以 **不要启用轮询**。真要做"后台提醒"，正确顺序是先让 EV 有"出站箱"，或者干脆只依赖 push。

## 九、已落地的「禁止重复提醒」改动（2026-09-27）

### 手环端 EV（`tom/class/class`，commit `9a0c4cf`，rpk 1.6.141）

1. `src/data/chat-bridge.js`：消息 `id` 从 `String(Date.now())` 改为 **`时间戳-随机4位`**。
   原因：只用毫秒时间戳时，同一毫秒连发两条会**撞 id** → 手机端会把第二条当成重复而**漏提醒**（比重复更糟）。
2. `src/app.ux` `syncHandleChatIncoming`：写入 `ev_chat_inbox` 的条目**补上 `id`**（缺失时自动生成），为将来拉取/去重留依据。

### APK（本仓 v0.5.16）

1. **修复"push 被静默丢弃"**：`SyncEngine` 原先在 `pending == null`（没有正在等待回包的请求）时**直接丢掉**手环推来的消息 —— 也就是手环主动发消息基本收不到。现在新增 `Observer`，无人认领的消息交给它处理。
2. **按 id 去重（核心）**：`MessageActivity.handleUnsolicited()` → `markSeen(id)`；已提醒过的 id 直接丢弃，**同一条只响铃/震动/弹窗一次**。已提醒集合存 `SharedPreferences`（保留最近 500 条）。
3. 兼容老 EV（无 `id`）：用 `ts + 文本哈希` 兜底去重。
4. 首页与留言页都在 `onResume` 重装观察者 → **只要 App 在前台，任何页面收到留言都会提醒**（去重是全局的）。

> 仍未做：进程被杀后的提醒（无解，需要前台服务 + 用户加省电白名单）；EV 侧的"出站箱"。
