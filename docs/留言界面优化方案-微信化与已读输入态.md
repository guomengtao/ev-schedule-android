> 生成时间：2026-10-04 22:59

> 状态：**方案（未实施）**——本文只定方案，不含代码改动
> 关联：`docs/手环发消息到手机-端到端实现与验收.md`（手环→手机链路）、`MessageActivity.java`（手机端留言界面）、`ev/class-schedule/src/pages/message-inbox/message-inbox.ux`（手环端留言板）

## 〇、一句话结论

现有留言页是「**离线留言卡片流**」——定位准确但不像聊天。本次把它升级成「**微信范式 + 真实回执**」：
气泡对话、真已读、看得见的输入态、可自定义快捷短语、少量可用表情；
但**每一条都要建立在"真实回执"上，宁可显示"未知"也不给假状态**。

## 一、现状（改前）

| 项 | 现状 |
|---|---|
| 界面 | `MessageActivity.java`：极简卡片流，无气泡、无左右对齐、无头像，最新在上 |
| 消息模型 | `{id, dir:"out"\|"in", text, ts, status:"pending"\|"sent"}`，存 SharedPreferences JSON 数组 |
| 协议 | 手机→手环 `chat`；手环→手机 `chat`（留言）/`chat_ack`（送达）/`rx_ack`（手机确认收到手环消息） |
| 送达判定 | 手环回 `chat_ack` → `status=sent`；超时/异常保留 `pending`，回页面自动补发 |
| 提醒 | 收到即响铃 + 震动 +（前台）弹窗；`seen_ids` 去重（上限 500） |
| 手环端 | `message-inbox.ux`：消息滚动区 + 横滑快捷短语 swiper + `phoneStatus`（读 `globalThis.__evSyncPhoneSeenTs`） |
| **缺口** | **无已读、无输入态、无草稿、无快捷按钮（手机端）、无表情** |

**关键定位差异**：现状文档明确写着"不是实时 IM，而是离线留言/消息通道"。本次优化的实质是——
**在不牺牲"离线可靠"的前提下，把"在线时"的体验做到像 IM**。这两者必须共存（断线仍能写、能补发）。

## 二、目标（用户指定的 5 点）

1. **界面微信化**：气泡对话风格
2. **已读功能**：尽量真实、准确（不准猜）
3. **输入中提示**：对方能看见"我正在输入"，且**未发送前就能看见我打的字**
4. **快捷按钮（手机端）**：几条常用语一键发送，并**支持自定义**
5. **表情/图标**：加几个有趣的小内容（用户预判"支持的很少"）

## 三、设计

### 3.1 视觉：气泡化（微信风）

改 `render()` 的布局层，消息模型不动：

- **我方（out）**：右对齐、主题色气泡、白字
- **对方（in）**：左对齐、浅灰气泡、深字
- **时间**：不每条都显示；与上一条间隔 > 5 分钟才插一条居中时间分割（微信规则）
- **头像**：手环端无头像 → 我方用内置"手机"图标、对方用"手表"图标（走 §3.7 Lucide 资产，不手绘）
- **输入栏**：底部固定；左侧快捷按钮入口、中间输入框、右侧发送；发送中状态显示在气泡上（见 3.2）
- **新消息**：收到底部自动滚到底；自己发送也滚到底（现状是"最新在上"，**要改成"最新在下"**才符合微信）
- **实现选型**：消息增多后 `LinearLayout` 全量重建会卡 → 用 `RecyclerView`（2 种 itemType），或维持重建但加 `ViewHolder` 缓存。**建议先维持现有重建方式（消息量小），超过 ~100 条再换 RecyclerView**，避免 P0 阶段引入重构风险。

### 3.2 已读：三级状态 + 真实回执（本方案的核心）

**语义定义（不许含糊）**：

| 状态 | 含义 | 判定依据 |
|---|---|---|
| 待发送 `pending` | 还没送达 | 本地队列默认态 |
| **已送达 `sent`** | **手环收到了** | 手环回 `chat_ack`（**已有**） |
| **已读 `read`** | **手环端留言页已展示该条** | 手环回 `chat_read`（**新增**） |

**为什么"已读"必须由手环上报，不能在手机端推断**：
手环被系统回收时，消息可能根本没到用户眼前。若用"手机已发出"当已读，就是**假状态**。
只有手环端真正**进入留言页并渲染了这条**，才允许上报已读。

**手环端上报规则（求真，防误报）**：
1. `message-inbox.ux` 的 `onShow` 后**延迟 ~600ms**（防一闪而过）再上报；
2. 上报范围 = **当次可见列表里的消息 id**（批量 `ids`），不报全量；
3. 用 `lastReportedIds` 去重，**同一条只报一次**；
4. 手环离线/被回收 → 不报 → 手机端状态**停在"已送达"**，这就是真实情况。

**手机端处理**：收到 `chat_read` → 把对应 `out` 消息 `status` 从 `sent` 升为 `read`；气泡右下角显示「已读 / 已送达」。

**反向（手机读手环消息）**：手机端打开留言页并渲染完手环消息后，同样上报 `chat_read`（同一 action，靠 `ids` 区分被读的是哪条）。手环端若要做"手机已读"提示，可复用；手环屏幕小，**该提示建议只放在详情/长按，不占列表**。

### 3.3 输入态：typing + 草稿实时可见

**两个层次，建议都做但要限流：**

1. **"对方正在输入…"**：输入框 `TextWatcher` 触发 → 节流发 `{"action":"typing","state":"start"}`；停止输入 ~1.5s 后发 `state":"stop"`。对面显示"对方正在输入…"。
2. **草稿实时同步（用户明确要的）**：把**当前已打的部分文字**随 typing 包带上 →
   `{"action":"typing","state":"upd","text":"<已打的字>","ts":…}`，对面**实时显示这段草稿**（灰色幽灵文字）。

**必须限流 + 防串台（否则 BLE 链路吃不消）：**

| 约束 | 建议值 | 理由 |
|---|---|---|
| 发送节流 | **≥800ms 一条**（文本变化才发） | interconnect 是事件推送，非流式长连接，高频小包会丢/延迟 |
| 文本截断 | 最多 **40 字**（取尾部） | 手环屏小 + 减包体 |
| 过期丢弃 | 收到 `typing` 时若 `now - ts > 3000ms` → **直接丢** | 乱序/延迟的草稿显示出来反而是错的 |
| 停止兜底 | 对面收到 `start/upd` 后 **5s 无新包** → 自动清掉输入态 | 防"卡住一直显示正在输入" |
| 清空时机 | 本端**发送成功后立即**发 `state":"stop"`（不带 text） | 避免草稿残留在对面 |

**手环端输入很少**（快捷短语/语音）：反向 typing 同样支持，但预期使用率低；**手环发短语时不发草稿，只发 `start`→直接 `stop`**（因为短语是"选"不是"打"）。

> ⚠️ **体验取舍要写清楚**：微信只显示"正在输入…"不显示草稿文字。本方案按用户要求**显示具体文字**，属于更"透明"的玩法——**实现上必须双端可关**（设置项），因为有人会介意。

### 3.4 快捷短语：默认 + 自定义 + 跨端一致

- **位置**：输入框上方一排**横滑**按钮（与手环端 `phrase-swiper` 交互一致）
- **默认几条**：`在上课` / `马上到` / `稍后回你` / `到了` / `好的`
- **自定义**：长按 → 编辑；存 SharedPreferences（JSON 数组，字段 `{text}`）；提供增/删/改/排序
- **跨端一致**：手环端已有 `src/data/reply-phrases.js`。**建议手机端短语独立存本地**（用户各自习惯），
  但**手环端短语可由手机端下发**（新增 `{"action":"phrases","list":[…]}`），避免两端各改各的。
  → 这一步涉及协议，放 P3；P1 先做纯本地。

### 3.5 表情 / 图标（用户预判"支持的很少"——预判正确）

**结论：不要指望 emoji。** 手环快应用的字体通常不含彩色 emoji，发出去极可能显示为**豆腐块 □**。
（本项目还踩过"jsc 内中文按 UTF-16LE 存储"的坑，说明字体/编码链路本就敏感。）

**双轨方案：**

- **轨道 A（主推，零字体风险）**：把表情做成**内置矢量贴纸**（走 §3.7 Lucide 规范生成，不手绘）。
  发送内容用**占位符**编码，如 `{{s:heart}}` / `{{s:ok}}` / `{{s:zzz}}`；两端渲染时替换成图片。
  好处：不依赖字体、可配色、可在手环上按屏幕缩放。
- **轨道 B（补充，需先实测）**：少量 **BMP 区符号**（`♥ ★ ✓ ♪ ☺ ⚡ ⌚` 这类）——**动手前先实测**手环渲染，
  能显示才纳入候选集；不能显示就只留轨道 A。

**动作顺序**：**先在模拟器 + 真机各发一遍候选字符，截图确认**，再定最终集合。
不要先写代码后发现在手环上是方块。

### 3.6 协议扩展（遵守跨端"只加不改不删"铁律）

**全部为新增 action，不改老字段**：

| 方向 | 报文 | 说明 |
|---|---|---|
| 手环→手机 | `{"action":"chat_read","ids":["a1","b2"],"ts":…}` | 已读回执（批量） |
| 双向 | `{"action":"typing","state":"start\|upd\|stop","text":"…","ts":…}` | 输入态 + 草稿 |
| 手机→手环 | `{"action":"phrases","list":[{"text":"…"}]}` | 短语下发（P3，可选） |

**⚠️ 必须处理的老端兼容坑（血泪教训，务必先测）**：
此前发现**老版本 EV 会把未知 action 当 `import` 处理并回 `no courses`**。
所以新增 action 前必须确认手环端 `app.ux` 的 `onmessage` 对**未知 action 是安全忽略**，
否则老包收到 `typing` 会触发奇怪的 import 回包，反而污染留言流。
→ **建议**：给所有新 action 加一个 `v` 字段，并在手环端 `onmessage` 里加一条"白名单外一律忽略且不回包"的兜底。

**复用已有能力**：`rx_ack`（手机确认收到手环消息）与 `chat_read` 语义不同，**不要合并**——
`rx_ack` = 手机"收到了"，`chat_read` = 手环"看见了"。两者刚好构成对称的可靠回执。

### 3.7 统一风险与坑

| 风险 | 应对 |
|---|---|
| **手环被系统回收** → 已读/输入态都收不到 | 状态**停在真实值**（已送达），绝不推断；UI 上"已读"缺失就是缺失 |
| interconnect 高频包丢/延迟 | 节流（3.3 的表）+ 过期丢弃 + 对面超时清态 |
| 老端收到未知 action 乱回包 | 3.6 的白名单兜底，**先测老包** |
| 消息多了 UI 卡 | 先维持重建式，超 ~100 条再上 RecyclerView |
| 主题适配 | 沿用现有 `Ui.themeVersion` + `recreate()` 机制，气泡配色取主题变量 |
| "最新在上"改"最新在下" | 是**行为变更**，要同步改自动滚动与空态文案 |

## 四、分阶段实施（每阶段一个会话，遵守总纲 §3.6「≤10 积分 / ≤5 分钟」）

| 阶段 | 内容 | 依赖 | 备注 |
|---|---|---|---|
| **P0** | 气泡 UI 微信化（左右对齐/时间分割/头像/底部输入栏/滚到底） | 无 | 纯界面，最安全，先做 |
| **P1** | 手机端快捷短语按钮 + 自定义（本地存储） | 无 | 纯本地 |
| **P2** | 已读回执：协议 `chat_read` + 两端上报/渲染 | P0 完成 | 需两端同改，注意老端兼容 |
| **P3** | 输入态 + 草稿：协议 `typing` + 限流 + 双端开关 | P2 之后 | 风险最高，最后做 |
| **P4** | 表情图标：先实测字体 → 定候选集 → 矢量贴纸落地 | 独立 | 可穿插，先花小代价实测 |

**执行纪律**：每阶段独立认领、独立提交、独立验收；**不许一个会话横跨两个阶段**。

## 五、验收标准

- P0：断线写留言 → 连上自动补发；气泡左右正确；时间分割符合 5 分钟规则；发送后自动滚到底
- P2：手环**进入留言页**后手机端显示"已读"；**手环未开机/未进页面时，手机端必须停在"已送达"**（这条是核心，用来证伪假状态）
- P3：连续打字只在对面显示一条"正在输入…"且草稿同步更新；**停止输入 5s 内对面输入态自动消失**；发送成功后对面草稿立即清空
- P4：候选字符/贴纸在手环上**截图确认不是方块**才算通过

---

## 六、明确不做 / 待定

- **不做**：已读回执的"已读时间戳展示"（手环小屏价值低）、消息撤回、群聊
- **不做**：把留言改成"纯在线 IM"——**离线可写 + 自动补发是底线能力，不能丢**
- **待定**：短语是否跨端同步（P3 再定）、贴纸集合最终名单（P4 实测后定）
- **待实测**：手环字体对 BMP 符号的渲染；老包对未知 action 的实际行为
