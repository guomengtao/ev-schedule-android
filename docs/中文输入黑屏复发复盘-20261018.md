## 三、真正没堵上的口子：`recreate()` 链（14~15 处）

`bb37f73` 把 `applyTheme` 改成「色板指纹变了才 `themeVersion++`」，挡住了**假变化**（widget 每分钟刷新的无条件自增）。
但挡不住**真变化**：「跟随手环」同步主题、系统深浅色切换、本地主题切换 —— 这些会让指纹真的变，`themeVersion` 照样上涨。

而 15 个 Activity 的 `onResume` 全是裸检测：

```java
// 修复前（15 处同款）
if (lastThemeVersion != 0 && lastThemeVersion != Ui.themeVersion) {
    recreate();
    return;
}
```

一旦 `themeVersion` 真的变了，**中文输入时**（输入法弹出 / 切面板 / 点键引起的生命周期抖动）回到 `onResume` 就会 `recreate()`：
窗口销毁重建 = **黑屏一瞬**；输入法随新窗口重新附着 = **「完成」键闪烁**。
这就是「昨天好了、今天又坏」的随机性来源 —— 取决于那段时间主题有没有真的变过。

## 四、本次修复（v0.5.179）

在 `Ui.java` 新增统一守卫，15 处检测全部改为走它：

```java
public static boolean needRecreate(Activity a, int lastVersion) {
    if (lastVersion == 0 || lastVersion == themeVersion) return false;
    if (imeVisible(a)) return false;              // 正在打字：绝不重建窗口
    long now = SystemClock.elapsedRealtime();
    if (lastRecreateAt != 0 && now - lastRecreateAt < 30000L) return false;  // 30s 防抖
    lastRecreateAt = now;
    return true;
}
```

改动面：
- `Ui.java`：新增 `needRecreate()` / `imeVisible()` / `lastRecreateAt`；
- 15 个 Activity：`if (lastThemeVersion != 0 && lastThemeVersion != Ui.themeVersion)` → `if (Ui.needRecreate(this, lastThemeVersion))`（脚本一次性替换，残留检查为空）。

设计取舍：键盘可见时**吞掉**这次主题重建（不补做）。主题变化不紧急，下次进页面自然会应用；换来的是「打字过程中窗口永不销毁」。

4. 判据：全程无黑屏、无「完成」键闪烁。

若第 3 步仍复现，则只剩两类可能，按此二分：
- **换 Gboard 仍现** → 不是输入法自身，是 App 窗口层（需抓 `adb logcat | grep -iE "recreate|InputMethod"`）；

## 七、教训

1. **「发布」不等于「上线」**：GitHub release 上传成功只完成 2/3，清单不 PUT，用户永远收不到（已复发 2 次）。
2. **修一个根因不等于修完**：H1 修完还有 H2，报告里 P1 第 5 条「onResume 检测加防抖」当时没做，这次就是它复发。
3. **验证要看用户设备上报的真实版本**，不要用「我构建了 / 我发布了」代替「他装上了」。`visitor_logs.device.app_version` 是唯一可信的装机事实。
