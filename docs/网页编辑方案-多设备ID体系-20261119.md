# 课程「网页编辑」方案 —— 多手机 / 多手环下的 ID 体系

- 日期：2026-11-19
- 状态：方案讨论稿（代码未动）
- 关联仓库：`ev/ev-schedule-android`（手机端）、`ev/class-schedule`（手环端）

---

## 0. 先回答你的疑问：`/user/<手机id>/<课程id>` 会乱吗

**会乱，而且是必然乱，不是概率问题。** 三条硬原因，都能在现有代码里指到行：

**① 现在根本没有「手机 id」这个稳定概念。**
手机端唯一的设备标识是手环的 BLE nodeId（`SyncEngine.currentDeviceId()`，来自配对时拿到的 `d.id`）。这是**手环的 id，不是手机的**。同一台手机换一个手环，deviceId 就变了；同一只手表配两台手机，deviceId 却是一样的。拿它当「用户」维度，等于把「手环」错当成「人」。

**② 课程 id 是「本机生成」的，同一门课在两台手机上必然不同。**
`CourseCache.Course.newId()` 返回 `c_<毫秒时间戳>_<4位随机hex>`。这是**随机主键**，不是业务主键。你在手机 A 加一门「周一 08:00 数学」，得到 `c_1763..._a1f2`；在手机 B 加同样的课，得到 `c_1763..._9c04`。两个 id，同门课。网页端按 id 编辑，只能改到其中一台那一份。

**③ 课表 id 会变，URL 会失效。**
`ScheduleStore` 里课表 id 有两条来源：
- 本地新建：`ev_local_<时间戳>`（第 286 行）
- 存入后：`watchId(deviceId, name)` = `ev_watch_<deviceId>::<课表名>`（第 318 行）

也就是说**一张表存进手环的那一刻，它的 id 就变了**；改个名，id 又变一次。任何把这个 id 写进 URL 的方案，都会在用户改名或首次存入后 404。

**结论**：URL 里的两级 id 如果直接用现有字段，会在「同一门课存在两份」「A 机加了 B 机不知道」「改名后链接失效」这三处同时出问题。要支持网页编辑，**必须先补一层真正的主键**，而不是复用现在的 id。

## 1. 现状（事实清单）

| 实体 | 现有标识 | 生成方式 | 稳定性 |
|---|---|---|---|
| 手环设备 | `deviceId` | BLE nodeId | 稳定但属设备不属人 |
| 课表（本地） | `ev_local_<ts>` | 创建时时间戳 | 存入后即失效 |
| 课表（手环镜像） | `ev_watch_<deviceId>::<名字>` | 设备 + 名字派生 | 改名即失效 |
| 课程 | `c_<ts>_<hex>` | 随机 | 本机唯一，跨设备不唯一 |
| 晚课模板 | `tpl_<sid>` | 跟随课表 id | 随课表 id 变化 |
| 账号 | **不存在** | — | — |

晚课模板这一行值得单独提：它按课表 id 存 key，所以**课表 id 一变，晚课配置就「丢」了**。这正是今天真机上「存入后凭空冒出一节晚课」的现象来源——新 id 找不到模板，走了历史迁移分支，把旧全局模板捡了回来。

## 2. 目标设计：三层主键 + 一个编辑凭证

### 2.1 三层主键

```
账号 accountId（人）           ← 归人，换手机/换手环都不变
  └─ 课表 scheduleGuid        ← 归「这张课表」，改名不变、存入不变
       └─ 课程 courseGuid     ← 归「这一节课」，跨设备同一个
```

**关键：`guid` 与现在的 `id` 并存，不替换。**
- `guid` 是 UUIDv4，**创建时生成一次，之后永不修改**，用于跨设备/服务端对齐；
- 现有 `id` 继续承担本机内部路由（页面跳转、模板 key、watchId 匹配），一行不改，零回归；
- 服务端只认 `guid`，本机内部只认 `id`，两者在落盘时同时写入。

这样做的代价是多存 36 字节 × N 门课，收益是**所有现存逻辑不动**。如果反过来「把 id 全换成 guid」，`watchId`、`tpl_<sid>`、`diffCount` 的匹配键全部要重算，回归面覆盖整个同步链路，不值得。

### 2.2 账号从哪来

不新建账号体系，复用现有 `app-auth.gudq.com`。最轻的三种入口，按优先级：

1. **设备码绑定**（推荐起步）：App 首次打开生成一个 `deviceSecret`（随机 32 字节，存私有目录），调一次接口换 `accountId`。零输入、零密码，用户无感。缺点是换手机要重新绑。
2. **手机号/邮箱登录**：换机可继承，但要接入注册流程，体验成本高。
3. **手环 nodeId 当账号**：**不要这么做**。理由见 §0 ①，手环是设备不是人，一换表就成新用户。

### 2.3 网页编辑的 URL 设计

> ⚠️ 本节为「直链凭据」方案。**主路径已改为 §2.4 的「扫码登录 + 手机端核对蓝牙 id」**，`#k` 片段凭据降级为临时一次性直链（24h）。本节保留作为 URL 可读段的依据与降级方案。

**主张：用「手环 MAC + 课表 guid」做可读定位段，但凭据必须另放。** 也就是你说的思路，改成下面这个形态：

```
https://app-auth.gudq.com/e/<watchMac>/<scheduleGuid>#k=<editKey>
```

拆开看三个段各自的职责：

| 段 | 内容 | 作用 | 能不能当凭据 |
|---|---|---|---|
| `/e/` | 固定前缀 | 路由 | — |
| `<watchMac>` | 手环 BLE MAC（`A4:C1:38:xx:xx:xx`） | **可读定位**：一眼知道是哪只表，日志里能追踪，客服能核对 | ❌ 公开可扫，不能鉴权 |
| `<scheduleGuid>` | 课表 UUID | **可读定位**：哪张课表 | ❌ 要配合凭据 |
| `#k=<editKey>` | 32 位随机串 | **唯一凭据** | ✅ |

### 为什么不能像你说的那样只用 `nodeid/<课程id>`

**① nodeId 本身不可靠。** `Stats.java:141` 里已经有现成证据：

```java
watch.put("mac_random", true);   // 占位/随机地址：服务端不得拿它当锚点
```

noteId 是 MiConnect 的**会话节点地址**，不是硬件身份。同一条注释（`Stats.java:247`）写得很清楚：「只有 BLE MAC / nodeId 跨重装、重置、换机稳定」——但实测中 nodeId 会出现随机地址形态，这类设备重连后 nodeId 会变。拿它进 URL，等于链接随时可能指向不存在的设备。

**要用的应该是 MAC**。项目里已经有现成探测：`Stats.probeWatchMacAsync(ctx, nodeId)`（`SyncEngine.java:423`，连接就绪就异步探一次），而且是「跨重装/重置/换机不变的设备锚点」（`Stats.java:133`）。

**② MAC 是可以枚举的，绝不能单独当编辑权。** 蓝牙 MAC 的厂商前缀固定、后 3 字节递增，扫一遍蓝牙就能收集一片。如果 URL 是 `/e/<mac>/<courseId>`，任何人都能：

- 拿到你的 MAC（站你旁边扫一下就行）；
- 猜课程 id —— 现有 `Course.newId()` 是 `c_<毫秒时间戳>_<4位hex>`，**时间戳部分是明文的**，知道大致添加时间就能在一个很小的时间窗里穷举；
- 直接打开编辑器改你的课表。

所以 `#k=` 这一段不是可选项，是这条 URL 能存在的前提。

**③ 课程 id 也不能直接进 URL。** 理由见 §0 ②③：`c_<ts>_<hex>` 是随机主键（跨设备不唯一），课表 id 会从 `ev_local_` 变成 `ev_watch_`（改名/存入即失效）。URL 里放的必须是 §2.1 那层 guid。

### 为什么 `#k=` 要放在 `#` 片段里

这是 OAuth2 隐式流的经典做法，不是随便选的：

- **片段不会发送到服务器**——浏览器发请求时只发 `?` 之前的部分，`#` 之后由本地 JS 读取；
- 因此它**不进 Nginx access log、不进 Referer、不进 CDN 缓存、不被中间代理记录**；
- 链接被截图/转发时，前两段够人读懂，后一段自动被很多客户端折叠。

代价：服务端拿不到它，必须由页面 JS 读出后用 `Authorization` 头或首次换 cookie 的方式提交。多一步 JS，但换来「凭据不进日志」，值。

### 三种设备的降级顺序

MAC 不是每次都能拿到（未连接、随机地址机型）。取凭据时按序降级：

1. `watchMac`（首选，跨重装稳定）；
2. `watchDeviceId`（手环通过 `get_device_id` 回的真实 id，`Stats.watchDeviceId()`）；
3. `nodeId`（最后兜底，URL 里标注 `random=1`，提醒链接可能失效）。

`deviceId4`（4 位短形）**不要进 URL**——只有 4 位，碰撞率太高，做展示都不合适。

### 服务端表结构

```json
{
  "editKey": "<32 位随机>",
  "watchAnchor": { "type": "mac", "value": "A4:C1:38:.." },
  "accountId": "...",
  "scheduleGuid": "...",
  "scope": "edit",
  "expiresAt": 1790000000,
  "revoked": false
}
```

`watchAnchor` 用 `type` 区分 mac / deviceId / nodeId，避免三种 id 混在一列里互相冒充。

### 备选：完全不可读的形态

如果你后面觉得「可读」没那么重要，可以直接退回：

```
https://app-auth.gudq.com/e/<editKey>
```

两段可读信息反正也能在页面标题里显示（「A4:C1:38 这只表的《八年级二班》」），URL 里有没有不影响用户体验，只影响排查效率。

### 2.4 主路径修正：扫码登录 + 手机端核对蓝牙 id

`#k=` 片段凭据的弱点是**「链接即权限」**——链接一旦被转发、被截图、被日志抓到，权限就跟出去了。改成「扫码授权 + 设备在场证明」之后，URL 本身不再是凭据，可以放心公开。

#### 2.4.1 为什么这条路更强

它证明的不是「你拿到了一个字符串」，而是**「你此刻手上正拿着那只手环」**。这是 possession proof（持有证明），安全等级高于任何一种可复制的 token：

| 攻击 | `#k` 片段 | 扫码 + 蓝牙核对 |
|---|---|---|
| 链接被转发 | 拿到即能改 | 只能看到「需要授权」，改不了 |
| 链接进了日志/Referer | 泄露 | 无所谓，URL 里没有权限 |
| MAC 被扫到后猜 URL | 猜中即可编辑 | 猜中只能触发一次「请求授权」，等你拒绝 |
| 别人拿你手机 | 能改 | 能改（这点两者一样，靠设备锁） |

#### 2.4.2 完整时序

```
① 网页  GET /e/<watchMac>/<scheduleGuid>
        ↓ 无有效会话 → 不是报错，而是渲染「请用手机确认」
        ↓ 页面显示一个大二维码 + 6 位数字 code（如 380417）
        ↓ code 有效期 120 秒，一次性

② 手机  App「网页编辑」页 → 扫一扫（或手输 code）
        ↓ App 收到 {code, scheduleGuid, watchMac, 请求来源IP/UA}

③ 手机  核对蓝牙 id  ← 关键一步，见 §2.4.3
        ↓ 核对通过 → 弹确认框：
        ↓   「网页请求编辑《八年级二班》」
        ↓   「设备：A4:C1:38:xx:xx:xx（已连接 ✓）」
        ↓   「来源：广东深圳 · 120.xx.xx.xx」
        ↓   [允许]  [拒绝]

④ 手机  点「允许」→ App 签名提交 → 服务端签发 session（7 天，可撤销）
        ↓ 网页轮询到 session → 自动跳进编辑器（无需刷新）
```

界面细节：网页端在等授权时**不要显示空白/转圈**，要显示「已向手机发送请求，请在手机上确认」，并留「用链接直连」的降级入口（见 §2.4.5）。

#### 2.4.3 「核对蓝牙 id」到底核对什么

这是这套方案的核心，必须核三样，缺一不可：

1. **连接状态**：App 当前 `nodeId != null`（`SyncEngine.hasNode()`）。没连着直接拒绝——连不上手环，就没法证明你在场。
2. **锚点匹配**：`Stats.watchDeviceId()` + `probeWatchMacAsync()` 拿到的 MAC / deviceId，与 URL 里的 `<watchMac>` 比对。
   - 相等 → 通过；
   - 不等 → 明确告知「这个链接指向另一只手环（A4:C1:38:**2F），你当前连的是 …**7A），是不是拿错链接了？」而不是笼统报「无权限」——用户能自己判断。
3. **课表归属**：`scheduleGuid` 在当前账号下存在，且确实绑在这只 `watchMac` 上。防止「链接里的 mac 对、guid 是别人的」。

**注意 1**：MAC 拿不到时（`mac_random` 机型）退回 `watchDeviceId` 比对，仍不行就要求用户在手环上确认（§2.4.4）。
**注意 2**：核对发生在**手机本地**，不把 MAC 上传给网页端。服务端只存「已授权」这个事实，不存实时设备指纹。

#### 2.4.4 可选加强：手环上确认一次

如果担心「用户无脑点允许」（钓鱼授权），可以让手环端也参与：授权时手环屏幕显示 4 位码，手机上要输入这 4 位才能完成授权。

- 成本：手环端 `class-schedule` 要加一个确认页面 + 消息通道；
- 收益：攻击者需要同时控制「手机确认」和「看到手环屏幕」，接近物理在场；
- 建议：**第一版不做**，先用「手机弹窗显示来源 IP/地区」顶住，观察是否真的出现钓鱼场景再加。

#### 2.4.5 和 `#k` 的关系

不是二选一，而是分层：

| 场景 | 用哪套 | 有效期 |
|---|---|---|
| 默认（网页编辑） | 扫码登录 + 蓝牙核对 | session 7 天 |
| 临时给家人改一次 | 生成 `#k` 直链 | 24 小时，一次性 |
| 只读分享（看课表） | 公开只读页，不含任何凭据 | 长期，可撤销 |

`#k` 只在「不方便扫码的临时场景」用，且强制短时效 + 单次使用（用过即失效）。

#### 2.4.6 URL 形态简化

有了登录态，URL 可以退回到纯可读，不含任何秘密：

```
https://app-auth.gudq.com/e/<watchMac>/<scheduleGuid>
```

- 别人打开 → 看到「请用手机确认」，什么也拿不到；
- 你自己打开 → 有 session，直接进编辑器；
- 打印/发群里也不担心，等于只泄露了「有这么一只表、有这么一张课表」。

这也顺带解决 §2.3 里「MAC 可枚举」的问题——**MAC 可枚举不再是问题，因为它不再是权限**。

#### 2.4.7 三个必须提前想清的坑

1. **必须在场才能编辑。** 手环没连手机 → 无法核对 → 无法授权。这会让「出门在外想改一下课表」变成做不到。缓解：session 有 7 天，连过一次就能改一周；7 天后必须重新连表确认。
2. **换手环后旧链接彻底废掉。** 这是正确行为（旧课表本来就不在新表上），但用户会困惑，需要在网页上明确提示「这只手环已不是当前设备，请从 App 重新生成链接」。
3. **多手机场景的身份归一。** 扫码授权产生的 session 属于「某个手机」，不是「某个人」。2 机 1 环时，两台机各自扫码各自的 session，都能编辑同一份数据 —— **仍然必须靠 §4 的 `rev` 乐观锁防并发覆盖**。扫码解决的是「谁能进」，不解决「两个人同时改」。

## 3. 多设备 / 多手环：逐个场景过一遍

这是你最担心的部分。逐个场景列清楚「会不会乱、靠什么不乱」。

| 场景 | 现状会不会乱 | 新方案下 |
|---|---|---|
| **1 手机 + 1 手环** | 正常 | 正常，guid 保证网页端能看到全部 |
| **1 手机 + 2 手环**（换表/双表） | **会乱**：两张 `ev_watch_<devA>::课表` 和 `ev_watch_<devB>::课表` 是两张独立表，晚课模板也各存一份 | 两张表各有 guid，是**两条独立数据**，网页端按 guid 分开展示，不会合并；用户想"一份课表推两只表"，靠「同一 guid 绑定多个 deviceId」实现 |
| **2 手机 + 1 手环** | **会乱**：两台手机各自维护一份本地表，存入时按名字覆盖同一份手环表，后存的赢，先存的用户不知情 | 靠 `accountId` 把两台手机归到同一人；同一 `scheduleGuid` 在两台机上指向同一份服务端数据，**冲突用版本号解**（见 §4） |
| **2 手机 + 2 手环** | **一定乱**：4 个 deviceId 组合，按名字匹配会互相覆盖 | 每台手机只对自己配对的 deviceId 负责；服务端按 `(scheduleGuid, deviceId)` 记录「哪张表推到了哪只表」，互不干扰 |
| **两台手机都给课表起名叫「未命名课表」** | **必然乱**（今天真机已验证过：8 份同名堆积） | guid 与名字解耦，同名不同实体，不再撞车 |
| **改课表名** | URL 失效、晚课模板 key 变更导致配置丢失 | guid 不变，URL 不变，晚课模板改按 guid 存 |
| **重装 App** | 数据丢失（全在 SharedPreferences） | `deviceSecret` 若存外部（系统备份/Account Manager）可恢复；否则需账号登录才能继承 |
| **网页编辑时手机也在改** | 无防护，后写覆盖先写 | 版本号乐观锁，冲突返回 409 让用户选（见 §4） |

一句话总结：**乱不乱不取决于有几台设备，取决于「这门课的身份」是否唯一。** 现在的身份是「名字 + 本机时间戳」，所以设备一多就撞；换成 guid 之后，设备数量只是「同一条数据有几个副本」，不再是「有几个不同的数据」。

## 4. 并发冲突：乐观锁 + 字段级合并

同步链路里已经有可复用的基础：`SyncCoordinator.merge(base, local, remote)` 是三方合并，`diffCount(base, courses)` 能算出差异。网页端接进来可以沿用同一套思路：

```
每条课程记录三个时间戳/版本：
  rev        单调递增整数，任何写操作 +1
  updatedAt  毫秒时间戳（已有字段，可直接用）
  updatedBy  写入方标识（deviceId 或 "web"）
```

**服务端写入规则**：

- 客户端带 `If-Match: <rev>` 提交；
- 服务端当前 rev ≠ 提交的 rev → **409 Conflict**，回包带上服务端版本；
- 客户端拿到 409 走字段级合并：
  - 两边改的字段不重叠 → 自动合并，rev+1；
  - 重叠 → 弹「这门课被改过，保留哪个？」（移动端弹窗 / 网页端 diff 视图）；
- `deleted` 是软删除标记（现有 `Course.deleted` 已在用），**删除优先于修改**，避免"删了又回来"。

**不做的事**：不要用「最后写入者赢」（Last-Write-Wins）。在课表这个场景里 LWW 会静默丢字段——手机改了教室、网页改了时间，LWW 只留下一个，用户不会收到任何提示。

---

## 5. 落地路径（分三步，每步可独立交付）

**第一步：只补 guid，不接网页（改动最小，先消除隐患）**
1. `Schedule` 加 `guid` 字段，`toJson`/`fromJson` 读写；老数据首次 load 时补生成（幂等）；
2. `Course` 加 `guid`，`ensureId()` 里一并补齐；
3. 晚课模板 key 从 `tpl_<id>` 改为 `tpl_<guid>`，加一次性迁移（老 `tpl_<id>` → `tpl_<guid>`，迁完删旧 key）。

这一步不涉及任何网络，纯本地改造，**收益是彻底消掉「改名/存入后晚课配置丢」和「同名表撞车」两个已实锤的 bug**。

**第二步：账号 + token 接口**
1. 设备码绑定换 `accountId`；
2. 服务端建三张表：`accounts` / `schedules` / `courses`，主键全用 guid；
3. 生成 `editToken` 的接口 + 手机端「网页编辑」入口（弹二维码）。

**第三步：网页编辑器 + 双向同步**
1. 网页端读一张课表的全部课程（按 guid）；
2. 提交走 `If-Match` 乐观锁；
3. 手机端同步时，把服务端变更合并进本地（复用现有三方合并）。

**顺序不能倒**：先做第三步会立刻撞上 §0 的三个问题，等于在沙地上盖楼。

---

## 6. 遗留风险（先说清，避免后面返工）

1. **`deviceSecret` 丢失 = 换新账号。** 重装/清数据后原课表无法继承。若要根治，必须上手机号或第三方登录，这是产品决策不是技术问题。
2. **guid 补生成时机**：如果两台手机同时对同一份旧数据补 guid，会生成两个不同 guid。仅当「旧数据已经在多端存在」时才发生。缓解：guid 一旦写入 `baseJson` 侧就固定，冲突时以「先写入服务端的为准」。
3. **网页端权限边界要明确**：editToken 泄露 = 整个课表可改。建议默认 7 天过期 + 手机端可见「当前有效链接」列表并可一键撤销。
4. **存储介质**：现在全部在 SharedPreferences（明文 XML）。上网页编辑后数据要出设备，至少要走 HTTPS + 服务端鉴权，`deviceSecret` 建议存 `EncryptedSharedPreferences`。

---

## 7. 需要你定的三件事

1. **账号入口选哪种**：设备码无感绑定（推荐起步）/ 手机号登录（可换机继承）/ 暂不做账号只做「单机导出链接」；
2. **「一份课表推多只手环」是不是真需求**：是 → guid 与 deviceId 做一对多绑定；否 → 保持一对一，实现简单一个量级；
3. **第一步（补 guid）要不要现在就做**：它不依赖任何服务端，且能直接修掉晚课配置丢失和同名撞车，是纯收益。
