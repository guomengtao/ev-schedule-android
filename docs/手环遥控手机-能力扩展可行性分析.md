# 手环遥控手机 · 能力扩展可行性分析

> 用户 2026-10-05 提出：手环工具箱已有「静音手机」，能否扩展更多遥控按钮 ——
> 手电筒 / 截屏 / 手机录音 / 回复微信 / 回复QQ / 查导航 / 问单词 / 查天气。
> **本文只做可行性分析，不含实现**（用户要求先分析）。

## 一、现状：链路已就绪，扩展成本极低

```
手环 tools.ux（item-row onclick）
  → chatBridge.sendCmd(type, params)          手环端只加 1 个按钮 + 1 个方法
  → interconnect
  → 手机 SyncEngine → CommandRouter.handle(json)   手机端只加 1 个 else-if + 1 个执行方法
  → 执行 + 回执 {"action":"cmd_result","type","ok","text"} 回手环显示
```

- **现有 4 条指令**：`find_phone` / `phone_status` / `mute` / `countdown`。
- **协议无需改动**：`{"action":"cmd","type":"<新类型>",...}` —— 新增能力＝**加一个 type**。
- 手机端 `CommandRouter.handle()` 是**白名单**分发；未知名静默消费。
- 类注释声明的安全基线：**「只认白名单 type，未知类型静默忽略；无对外发送 / 涉账号操作」**（见 §五，这条决定了 7、8 两项要不要碰）。

> 结论：**技术接入几乎零成本**，真正的门槛在「权限」「隐私」「合规」，不在代码。

## 二、逐项可行性

| # | 功能 | 实现原理 | 权限 / 门槛 | 难度 | 主要风险 |
|---|---|---|---|---|---|
| 1 | **手电筒** | `CameraManager.setTorchMode(id,on)`(API23+)；老机 `Camera1`+`setFlashMode` | 一般**免权限**（个别 ROM 需 CAMERA） | ⭐ 易 | 低。需探测"有闪光灯的 cameraId" |
| 2 | **查天气** | 联网 API（和风/OpenWeather）或拉起天气 App | INTERNET（+定位可选） | ⭐ 易 | 低。城市可用定位自动取 |
| 3 | **问单词** | 词典 API / `ACTION_PROCESS_TEXT` 转交词典 App | INTERNET | ⭐ 易 | 低。**瓶颈是手环输入**（见 §四） |
| 4 | **查导航** | `Intent(ACTION_VIEW, geo:/导航)` 拉起地图；或预设"回家/公司" | 无 | ⭐ 易 | 低。目的地同样有输入瓶颈 |
| 5 | **手机录音** | `MediaRecorder` + 前台服务持续录 | `RECORD_AUDIO` 运行时授权 + `FOREGROUND_SERVICE` | ⭐⭐ 中 | 隐私敏感；需"录音中"明显提示 + 一键停 |
| 6 | **截屏** | `MediaProjection` + 常驻前台服务；或 root | **首次必弹系统授权框（须在手机上点）**，无法纯手环绕过 | ⭐⭐⭐ 难 | 首授无法自动化；常驻服务；截屏内容敏感 |
| 7 | **回复微信** | ① 通知 `RemoteInput` 直回；② `AccessibilityService` 模拟点击 | 通知使用权 / 无障碍服务 | ⭐⭐⭐ 难 | **违反微信条款**、随版本失效、稳定性差；**突破"不涉账号"基线** |
| 8 | **回复QQ** | 同微信 | 同微信 | ⭐⭐⭐ 难 | 同微信 |

## 三、结论：三档

- **A 类 · 建议做（低风险，纯代码，无需特殊权限）**
  手电筒 · 查天气 · 问单词 · 查导航
  → 完全落在现有白名单范式内，半小时级别一条。

- **B 类 · 可做，但要"权限 + 前台服务 + 隐私明示"**
  手机录音
  → 需运行时授权 + 常驻服务；必须给用户"正在录音"的显式状态与一键停止。

- **C 类 · 不建议自动做**
  - **截屏**：`MediaProjection` 首授**只能在手机上点**，与"手环一键"矛盾；要做得接受"先从手机授权一次"。
  - **回复微信 / QQ**：依赖无障碍或通知直回，**易随 App 版本失效**、有账号风险，且**直接打破** `CommandRouter` 声明的"不涉账号 / 不对外发送"安全边界。

## 四、手环侧的真正瓶颈：输入

天气 / 单词 / 导航都需要**参数**，而手环打字极难（小屏 + 无中文输入）。解法：

| 需求 | 免输入方案 |
|---|---|
| 查天气 | 用**手机定位**自动取当前城市，手环只按一下 |
| 问单词 | **手机端输入**单词（复用留言/短语），手环看结果；或手环查"最近/预置词" |
| 查导航 | 预设**"回家 / 去公司"两个快捷**；复杂目的地走手机端 |
| 通用 | 复用现有**快捷短语**机制当参数载体 |

## 五、安全与合规边界（必须划线）

现有 `CommandRouter` 明确"**无对外发送 / 涉账号操作**"。第 6~8 项会突破它：

- 回复微信/QQ = **代用户对外发送 + 操作第三方账号** → 越权语义。
- 无障碍自动化在微信/QQ 上**易被判定异常**，且会随对方版本更新而失效（维护无底洞）。
- 建议**不做自动回复**；替代：
  - 手环收到"有人找你"→ 手机端**通知提醒你去回**；
  - 或**预填草稿**，由用户自己按发送（用户仍是操作主体）。

## 六、若决定做：推荐批次

- **第 1 批（A 类，低风险）**：手电筒 · 查天气 · 查导航(回家/公司) · 问单词(手机端输入)
- **第 2 批（B 类）**：手机录音（含"录音中"提示 + 一键停）
- **暂不做**：截屏（首授矛盾）、微信/QQ 自动回复（合规 + 稳定性）

## 七、待定（需用户拍板）

1. 原话"先分析，这个不…"的**后半句**：是做还是不做？
2. 若做，**先做哪几条**？
3. 参数型（天气城市 / 单词 / 目的地）**交互怎么定**（定位自动取？手机端输入？预设快捷？）
