# 「提示没装小米运动健康」误报修正与兜底方案

- 日期：2026-11-05 15:54 +0800
- 涉及项目：`ev/ev-schedule-android`（手机端同步器 APK）
- 性质：**方案文档，不含代码改动**
- 关联文档：`docs/防止连接第一步卡住-方案-20261105.md`（同一链路的另一个缺陷：无超时）
- 用户反馈：「明明装了小米健康，它却提示连这个都没安装」

---

## 零、结论

**检测口径错了，不是小米健康没装。**

`api == null` 判的是「穿戴 SDK 的 MessageApi 门面有没有拿到」，
代码却把它直接翻译成「还没装小米运动健康」。这两件事不等价：
包可以好好装着、手环也连着，但 SDK 门面照样可能因为服务未绑定、类初始化失败、
系统后台限制而拿不到。

现场实测（USB 真机 `BLN-AL20` / Android 8.0 / EMUI 8.0）：

| 事实 | 值 |
|---|---|
| 实际安装 | **`com.mi.health` 3.59.1** |
| 同步器 | `com.application.watch.classschedule` 0.5.181 |
| App 的拉起逻辑认识的包 | `com.xiaomi.wearable` / `com.xiaomi.health` —— **都不包含 `com.mi.health`** |

也就是说，除了文案误报，「打开小米运动健康」这个恢复按钮在现网机型上**必然失败**，
会报「未找到小米运动健康，请手动打开」。这是同一个根因的第二个症状。

---

## 一、四处同源误报（代码定位）

| # | 位置 | 现状 | 问题 |
|---|---|---|---|
| E1 | `SyncEngine.java:198-205` | `api = Wearable.getMessageApi(c)`，`catch(Throwable)` 后 `api=null` | 把「SDK 门面不可用」当成「包未安装」的判据 |
| E2 | `SyncEngine.java:66,68,77` | `private static SyncEngine inst` 单例，`api` 只在构造时求一次 | **一次性快照**：后来小米运动健康启动了、服务可用了，`api` 仍是 null，永远报没装，没有任何重试 |
| E3 | `DebugActivity.java:684-686` | `openMiFitness()` 只试 `com.xiaomi.wearable` / `com.xiaomi.health` | 包名白名单过时，漏掉现网主流的 `com.mi.health` |
| E4 | `SyncEngine.java:1537`、`:1329`、`:359`、`:1307/:1331` | 四处写「还没装小米运动健康」「请安装并打开…」 | 同一个错误归因被复制了四份，改一处不够 |

值得注意：`SyncEngine.java:1272` 已有一条注释——

> 「极易被误读成『手机上的 App 没装』。真实含义是：手环侧没有同包名的快应用（EV 课程表）」

说明项目里**已经识别并修过同类误归因**（手环侧 EV 未装 vs 手机侧 App 未装），
但 `step1` 这条链路没有同步修正。这不是偶发笔误，是模式性问题：
**「拿不到某个 SDK 对象」被习惯性写成「用户没装某个 App」**。

---

## 二、正确的检测分层：把一个问题拆成五个可判定的事实

现在 `api == null` 一个布尔值承担了五种完全不同的结论，必然误报。建议改成：

| 层 | 判据（都是只读、零 SDK 依赖） | 能回答的问题 |
|---|---|---|
| L1 包是否存在 | `PackageManager.getPackageInfo(pkg, 0)`，遍历白名单 | 到底装没装 |
| L2 版本 | `PackageInfo.versionName` | 是不是过旧/过新的版本 |
| L3 服务是否声明 | `resolveService(new Intent("com.xiaomi.wearable.XMS_WEARABLE_SERVICE"), 0)` | 该版本是否还提供穿戴服务 |
| L4 绑定结果 | `bindService` 返回 + `onServiceConnected` + 超时 | 系统有没有放行这次跨进程调用 |
| L5 SDK 门面 | `Wearable.getMessageApi(c)` 是否可用 | 客户端能不能发消息 |

**`api == null` 属于 L5，不能用来回答 L1。** 只有 L1 明确查不到包时，
才允许出现「未安装」字样；L3/L4/L5 失败一律归类为「服务不可用」，并带上具体原因。

> 实现提示：Android 11+ 需要在 `AndroidManifest.xml` 声明 `<queries>`
> 才能查到第三方包与服务；现场机是 Android 8 不受影响，但方案必须覆盖新系统，
> 否则未来会出现「明明装了却查不到」的第二代误报。

---

## 三、文案矩阵：四种结论分别说什么

| 判定 | 建议文案要点 | 一键动作 |
|---|---|---|
| L1 未安装 | 「这台手机还没安装小米运动健康」 | 去应用商店 / 扫码下载 |
| L1 已装、L2 版本过低 | 「当前版本过旧，请升级小米运动健康」 | 打开应用市场 |
| L3 服务不可解析 | 「当前版本不提供穿戴服务，自动同步暂不可用」 | **直接给兑换码入口** |
| L4/L5 绑定或门面失败 | 「小米运动健康装着，但连不上它的服务」+ 说明可能被后台限制 | 拉起 App、后台运行设置、重试 |

禁止出现：把任何 L3/L4/L5 失败笼统写成「没装 / 请安装」。

## 四、兜底方式清单（按「检测 / 恢复 / 业务 / 诊断」四组）

### 4.1 检测兜底（先别下结论）

1. **包名白名单扩展**，按优先级依次探测：
   `com.mi.health`（现网国内版，实测 3.59.1）→ `com.xiaomi.wearable` →
   `com.xiaomi.hm.health`（旧「小米运动」）→ `com.xiaomi.health`（保留兼容）。
   **白名单必须集中成一个常量表**，禁止像现在这样散落在各 Activity 里各写一份。
2. **服务可解析判定**：`resolveService` 分别对每个包探测，命中哪个就记哪个包名与版本。
3. **`getLaunchIntentForPackage` 兜底**：如果白名单全不中，用 `PackageManager` 查询
   含 `health/wearable` 关键词的可启动包，列出候选让用户选，而不是直接判「没装」。
4. **`<queries>` 声明**（Android 11+），避免包可见性限制导致假阴性。

### 4.2 恢复兜底（连不上时主动救）

5. **允许重新初始化**：`api` 不要一次性缓存成不可变状态；提供
   `SyncEngine.rebind()`，在用户点「重试」或小米运动健康回到前台时重新取 `getMessageApi`。
   这一条直接解决 E2「永远报没装」。
6. **修正拉起逻辑**：`openMiFitness()` 改用 4.1 的白名单（`DebugActivity.java:684`），
   拉起后延迟 2-3 秒再触发一次 L4 判定，不要立刻下结论。
7. **后台运行引导**：EMUI / MIUI / 鸿蒙上给「允许自启动、关闭电池优化」的
   明确指引（可跳系统设置页）。现场机正是 EMUI 8，这条命中率最高。
8. **退避重试**：1s → 3s → 8s，最多 3 次；每次都重新走 L1→L4，
   避免拿旧快照判新状态。
9. **保留 `api == null` 的保护，但只改归因**：不要删掉判空，
   只是把它从「未安装」改成「服务不可用」，并附带 L1 的真实结果。

### 4.3 业务兜底（自动同步不可用，功能也不能断）

10. **兑换码激活**：连不上就直接引导到 `ev/class-schedule` 的兑换码路径，
    只依赖一个网页，不碰蓝牙、不碰小米运动健康
    （依据 `ev/class-schedule/docs/激活入口顺序调整方案-20261104.md`）。
11. **手环端自显设备 ID**：手环上直接展示 4 位设备 ID，用户手输到网页换码，
    完全不需要手机端同步器参与。
12. **AstroBox / EV 安装器装机通道**：同步器只负责「同步」，装机与激活不必绑在它身上。
13. **失败态不阻塞其它功能**：课表编辑、表盘、导入等本地能力保持可用，
    不要像现在这样把「腕聊/工具/昵称」整块收起只留一个卡住的页面。

### 4.4 诊断兜底（下次不用靠猜）

14. **UI 上给「复制诊断信息」**：把 L1~L5 的逐层结论、
    `os_brand` / `android_sdk` / `mi_health_pkg` / `mi_health_ver` /
    `service_action_resolved` / `bind_result` 拼成一段可复制文本。
15. **埋点补齐**：复用 `docs/apk-tracking-telemetry-spec.md` 的
    `connect_last_fail_step` / `connect_last_fail_reason`，新增上述环境字段，
    远程即可判定「包没装 / 服务不可解析 / bind 被拒 / 门面失败」。
16. **区分已知不支持环境**：鸿蒙 NEXT「卓易通」沙箱直接判不支持，
    不要让用户反复重试（该结论已在埋点规范 §四记录）。

## 五、落地顺序与最小改动集

| 序 | 动作 | 位置 | 收益 |
|---|---|---|---|
| 1 | 抽出统一的包名白名单常量表 | 新增 `MiHealthPackages.java`（或 `SyncEngine` 静态表） | 消掉 E3 与未来的散落硬编码 |
| 2 | L1/L2/L3 三层 Preflight | `SyncEngine` 新增 `preflight()` | 从根上消除「已装却报没装」 |
| 3 | 四处文案按矩阵改写 | `SyncEngine.java:1537,1329,359,1307/1331` | 消除 E4 |
| 4 | `rebind()` + 退避重试 | `SyncEngine.java:66-77` | 消除 E2 |
| 5 | `openMiFitness()` 接白名单 | `DebugActivity.java:684` | 恢复按钮在现网机型可用 |
| 6 | 兑换码兜底入口 + 诊断复制 | `BandActivity` / `DebugActivity` | 用户不再被卡死 |

**只做 1+2+3 就能保证「装了却说没装」不再出现**；4 解决「重启后一直误报」；
5、6 保证失败时仍可自救。建议 1~5 同批上线，6 随后。

| 场景 | 期望 |
|---|---|
| 现场机 `BLN-AL20` + `com.mi.health` 3.59.1 | 显示「已安装 3.59.1」，绝不出现「没装」；服务不可解析则给兑换码入口 |

## 七、边界

- 不改 `xms-wearable.jar`，不逆向小米 SDK；判定全部走 `PackageManager` 与已有公开 API。
- 不改变「自动同步」的能力边界：后台策略、账号登录、Mi Fitness 版本仍由外部决定。
- 不动 `ev/class-schedule` 手环端；兑换码与手输设备 ID 按现状复用。
- 与 `防止连接第一步卡住-方案` 是互补关系：那份解决「无限等待」，
  这份解决「错误归因 + 无兜底」，两份的 Preflight 层可合并实现，不要做两套。

---

## 八、一句话复盘

**把「SDK 拿不到对象」写成「用户没装 App」，等于把自己的不确定性甩给用户。**
判据要分层、结论要对应到层、每层失败都要给一条走得通的路——
这才是「兜底」，而不是多写几句安慰文案。
